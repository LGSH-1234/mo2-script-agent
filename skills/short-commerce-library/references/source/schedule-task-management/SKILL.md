# 定时任务管理

帮用户把「到某个时间自动发起一次 Agent 执行」这件事落地并管理起来。所有操作都通过 `schedule_manage` 一个工具完成，用 `action` 字段区分具体动作。

## 核心概念

- **定时任务计划（plan）**：一条「到期触发规则 + 要执行的指令」。到触发时间时，系统会**新开一个会话**、把计划里的 `prompt` 作为指令自动跑一次。
- **触发方式（trigger_type）**：
  - `once`：单次，在 `fire_at` 指定的时间触发一次。
  - `cron`：周期，按 `cron_expr`（5 段分钟级 cron）重复触发，**最小间隔 1 小时**。
- **prompt 必须自包含**：到期执行时是一个全新会话，读不到当前对话上下文。所以写进计划的 `prompt` 要能独立看懂、独立执行（把主题、风格、数量等关键信息都写进去）。
- **执行归属**：计划由 Agent 代用户创建（记 `created_from=agent_tool`），执行时按用户身份发起。

## 何时使用

用户表达出「让某件事在未来自动/周期性发生」时，例如：
- 「每天早上 9 点帮我生成一张励志海报」→ cron，每天 9:00
- 「工作日下午 6 点提醒我总结当天进展」→ cron，工作日 18:00
- 「3 分钟后 / 今晚 8 点生成一段猫咪视频」→ once
- 「我有哪些定时任务」「把那个每天的任务停了」「删掉 XX 计划」→ 查看 / 暂停 / 删除

不要在用户只是想「现在马上做」时创建定时任务——那种直接用对应的生成工具即可。

## 操作速查（action）

| action | 作用 | 必填参数 |
|--------|------|----------|
| `create` | 创建计划 | `name`、`trigger_type` + (`fire_at` 或 `cron_expr`)、`prompt` |
| `list` | 列出我的计划 | 无（可选 `status`、`page`、`page_size`） |
| `get` | 查看某计划详情 | `schedule_plan_id` |
| `update` | 修改计划（名称/触发/prompt） | `schedule_plan_id` + 要改的字段 |
| `update_status` | 暂停 / 恢复 | `schedule_plan_id`、`status`（`paused`/`active`） |
| `delete` | 删除计划 | `schedule_plan_id` |
| `list_executions` | 查看某计划的执行记录 | `schedule_plan_id` |

## 创建参数说明

- `trigger_type=once`：填 `fire_at`，格式 `"2026-07-18 09:00:00"`（按 `timezone` 解释，默认 `Asia/Shanghai`），必须晚于当前时间。
- `trigger_type=cron`：填 `cron_expr`，5 段 `分 时 日 月 周`，最小间隔 1 小时。可选 `execute_limit`（执行次数上限，0=不限）。
- `prompt`：到期要执行的自包含指令。
- `agent_name`：一般不用填，默认沿用当前 Agent。

### 常用 cron 速查

| 需求 | cron_expr |
|------|-----------|
| 每天 9:00 | `0 9 * * *` |
| 每天 21:30 | `30 21 * * *` |
| 工作日 18:00 | `0 18 * * 1-5` |
| 每周一 10:00 | `0 10 * * 1` |
| 每小时整点 | `0 * * * *` |

（cron 第 5 段星期：0=周日、1=周一 …… 6=周六）

## 定时任务 Prompt 编写指导

创建或修改定时任务时，`prompt` 不是简单复述用户一句话，而是未来到点执行时 Agent 会收到的**完整任务说明**。到期执行发生在新会话里，Agent 读不到创建时的上下文，因此要把用户意图加工成可独立执行的详细 prompt。

### 验证流程

写入 `prompt`前，先询问用户是先跑一次尝试链路还是只创建定时任务，建议问卷默认是先跑一次尝试链路，如果是在上文中已经跑过整个链路之后可以不询问，还有创建的时间。

- 只创建任务就根据下面的要求创建。
- 尝试跑一次链路就先根据用户的要求跑相关流程，加载哪些skill，使用什么工具执行要自己清楚。跑完用户觉得没问题了再去写相关 `prompt`.

### Prompt 必须包含的信息

写入 `prompt` 前，先把下面信息补齐；用户没说清时，优先追问，或在低风险场景给出合理默认并写进 prompt：

1. **任务目标**：到点要完成什么事，不只写「帮我处理一下」。
2. **背景与输入**：涉及的主题、对象、账号、项目、素材、链接、数据范围、时间范围等。
3. **执行步骤**：期望 Agent 怎么做，先加载哪些SKill，是否进入规划模式、先查什么、再生成什么、是否需要对比、是否需要总结，记住这里最好填写最优路径，不要尝试时的错误路径写到里面。
4. **最终产物**：明确交付物形态，例如一段文案、3 个标题、Markdown 表格、海报生成请求、日报摘要、待办清单、发送前草稿等。
5. **质量标准**：风格、长度、语气、语言、数量、格式、禁忌、是否需要可直接复制使用。
6. **失败/不确定时的处理**：缺数据、权限不足、外部接口失败、信息不确定时，应该报告原因和下一步，而不是编造结果。

### 编写原则

- **自包含**：不要写「按上面说的」「照刚才那个」「继续昨天的」这类依赖当前会话的说法；要把引用内容改写进 prompt。
- **可执行**：避免只写愿望，改成明确动作。例如不要写「提醒我运营日报」，应写「整理今天 00:00-24:00 的运营数据变化，输出 3 条结论和风险项」。
- **产物明确**：必须说明最终要给用户什么。没有产物定义时，Agent 到点后容易只泛泛回复。
- **边界清楚**：周期任务尤其要写清每次执行的时间窗口，例如「统计过去 24 小时」「总结上一个工作日」「生成下周一要发的内容」。
- **保守处理外部动作**：如果任务涉及发布、发送、删除、扣费、改配置等高风险动作，prompt 应要求先生成草稿/方案并等待确认，除非用户明确授权自动执行。

### 创建/修改时的加工流程

1. 从用户原话里抽取：触发时间、任务目标、输入范围、产物要求、风格/格式要求。
2. 判断 `prompt` 是否能在新会话里独立执行；如果不能，把缺失上下文补写进去。
3. 把口语化诉求改写成结构化指令，优先用「目标 / 输入 / 步骤 / 输出要求 / 异常处理」组织。
4. 调 `schedule_manage` 前，确认写入的是加工后的完整 prompt，而不是用户原话片段。
5. 修改定时任务内容时，要重新生成完整 prompt；不要只追加一句模糊补丁，避免旧 prompt 与新要求冲突。

### Prompt 模板

```text
目标：<到点要完成的任务>。
背景/输入：<必要上下文、对象、数据范围、素材、链接、时间窗口>。
执行要求：
1. <步骤 1>
2. <步骤 2>
3. <步骤 3>
输出要求：<最终产物形态、数量、格式、语言、风格、长度>。
异常处理：如果缺少必要信息或执行失败，请说明缺什么/失败原因，并给出下一步建议；不要编造不存在的数据。
```

### 示例

用户说：「每天早上 9 点提醒我发小红书」。不要直接把 prompt 写成「提醒我发小红书」。应加工为：

```text
目标：为用户准备当天要发布的小红书内容草稿。
背景/输入：主题围绕小云雀 AI 创作工具的日常使用技巧；面向中文内容创作者。
执行要求：
1. 先给出 1 个当天适合发布的选题。
2. 生成 1 段小红书正文草稿，语气自然、有实操感。
3. 生成 3 个可选标题和 5 个相关话题标签。
输出要求：用 Markdown 输出，包含「选题」「正文」「标题备选」「话题标签」四部分，正文控制在 300 字以内，可直接复制发布。
异常处理：如果无法获取当天热点，就基于常青技巧选题生成，不要声称引用了未验证热点。
```

用户说：「每周一帮我总结项目」。应加工为：

```text
目标：生成 agent-schedule-task 项目的周度进展总结。
背景/输入：总结范围为上一个自然周内与定时任务能力相关的需求、开发、部署、验证和阻塞进展。
执行要求：
1. 汇总已完成事项、进行中事项、风险/阻塞、下周建议。
2. 对涉及 commit、部署、MR、验证结果的信息，能查到就列出稳定标识；查不到时说明缺失。
3. 不要编造不存在的进展。
输出要求：用 Markdown 输出，包含「本周完成」「当前风险」「下周计划」「需要用户决策」四节，每节用 bullet list。
异常处理：如果无法访问项目资料，请说明无法访问的来源，并给出用户可补充的信息清单。
```

## 典型流程

**创建**
1. 判断单次还是周期：出现「每天/每周/工作日/每小时」→ cron；出现具体某个时间点或「N 分钟/小时后」→ once。
2. 把用户要做的事整理成自包含 `prompt`。
3. 调 `schedule_manage`，`action=create`，带上 `name`、`trigger_type`、时间参数、`prompt`。
4. 成功后用一句话把「什么时候、会做什么、下次执行时间」回给用户；工具返回里有 `schedule_plan_id`，记住它以便后续管理。

**查看 / 管理**
- 用户问「有哪些定时任务」→ `action=list`，把每条的名称、触发规则（`trigger.human_readable`）、下次执行时间、状态列给用户。
- 用户要停/恢复某条 → 先 `list` 或 `get` 拿到 `schedule_plan_id`，再 `action=update_status`。
- 用户要改时间或内容 → `action=update`，只传要改的字段。
- 用户要删 → `action=delete`。
- 用户想知道「跑没跑、跑成啥样」→ `action=list_executions`，看每次执行的状态、时间和产出会话。

## 注意事项

- 时间信息要问清或合理默认，避免创建出「过去时间」的 once 计划（会被拒绝）。
- 周期任务间隔不能小于 1 小时，遇到「每分钟/每 5 分钟」的诉求要向用户说明限制。
- `prompt` 一定要自包含；如果当前对话里有关键上下文（风格、主题、参考），要显式写进 `prompt`。
- 创建/修改后，把关键信息（下次执行时间、计划名）简洁回给用户确认，不要把工具原始 JSON 直接倒给用户。
- 工具报错（如超出配额、未开放等）时，用一句话把原因转达给用户，不要静默重试。
- 定时任务创建/修改好后要及时跟用户同步修改/创建的定时任务。如果是创建定时任务在创建完成后**明确说明你的步骤和交付产物**，以防用户不知道你去做他不知道的操作。
- 创建好定时任务后，可以让用户点击页面右上角的头像框查看当前的定时任务有哪些以及相关调度情况。
- [IMPORTANT]如果是进入规划模式或者加载某些skill才做成的流程, **必须在prompt中写清楚需要进入规划模式/加载 `skill-name` 技能**。
- 为了保证定时任务所产生的结果不会被其他线程覆盖，如果设计到文件创建等操作，需要保证文件路径中含有精确到秒的时间的命名方式。
- 定时任务如果用户设置整点时间需要提醒用户可能会因为高峰期导致定时任务可能会稍晚执行，属于正常现象。
- 定时任务设置好后要提醒用户每个定时任务有效期为一周，到期会自动关闭需要再手动打开续期。
- 定时任务现在仅会员可用，会员活跃的定时任务最多存在三个。
