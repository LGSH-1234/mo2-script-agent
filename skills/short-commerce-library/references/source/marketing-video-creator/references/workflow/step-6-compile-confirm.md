
# 工作流 · 第 6 步：学习生成指导、编译最终方案并确认

> 本文件是第 6 步的权威正文。进入本步时即时读取。

## 6. 学习生成指导、编译最终方案并确认

**先按用户所选 AI 视频生成模型加载对应的 Seedance 编译指导文件（按版本只加载下表其中一份），它是本步把已确认内容翻译成该模型能直接吃的 Prompt 语法。每份版本文件都以 `../ai-prompt-guide/_shared-compiler-rules.md`（版本无关的共享编译规则）为基座，须与版本文件配套读——版本文件只承载该版本的差异，共享正文在 `_shared-compiler-rules.md`：**

| 路由条件 | 加载的生成指导文件 |
| --- | --- |
| 运行时/用户选定 Seedance 2.0 模型 | [Seedance 2.0 编译指导](../ai-prompt-guide/seedance-2.0.md) |
| 运行时/用户选定 Seedance 2.5 模型 | [Seedance 2.5 编译指导](../ai-prompt-guide/seedance-2.5.md) |

用[协作与质量](../base/collaboration-and-quality.md)的生成前方案检查（其权威正文在那里，按「全局文件读取设置」读到末尾再据以执行），从权威输入、故事脚本、实际素材和当前能力快照编译出确切的运行时请求，落成 `视频生成Prompt.md`（严格按最终生成信息格式，字段级正文见 [frozen-formats.md](../base/frozen-formats.md)「最终生成信息格式」，直接读该小节即可，不必整读 intake）。**本步呈现与确认所依据的权威合同（「交付范围路由合同」「动态表单合同」「沙箱产物约束」「呈现文件让用户确认」）都在根级 `contract-interaction-products-delivery.md` 里；进入本步前必须对 `contract-interaction-products-delivery.md` 过 SKILL.md 不变量 #14「真读门」，下文按合同名引用它们（含 `视频生成Prompt.md` 冻结格式、`present_sandbox_file` / `dynamic_questionnaire` 用法）时指的就是这份 contract 的正文。** 呈现前先跑生成前方案检查。

**合同校验不得代替最终 Prompt 校验。** 先用 `scripts/validate_creative_contract.py` 检查选择逻辑，写完每个 `视频生成Prompt*.md` 后，必须再用 `scripts/validate_final_prompt.py <prompt> --contract <internal-contract.json>` **直接扫描实际要投喂的文本**。内部 contract 放禁止项列表 `forbidden_sku_terms`/`unsupported_claim_terms`/`forbidden_imports`；有已选 Hook 时还必须原样带入第 3 步通过的 `hook_acceptance_contract`，不得为迁就最终 Prompt 而删减。**`--contract` 在参数层面已是可选（漏传不再报 argparse usage），但这只是为了让报错可读，不代表可以跳过验收门：有 Hook 时必须传，否则 Hook 追溯门整个不会执行**（省略时返回里会带 `note` 提示禁止项未被检查）。只有纯禁止项、无 Hook 的场景才可用内联 JSON，如 `--contract '{"forbidden_sku_terms": ["钢丝球"]}'`；带 `hook_acceptance_contract` 时一律走文件路径。路径写错会返回中文 `errors` 并退出 1，按字面改路径即可，不要去读校验器源码。**这两个校验器所需 JSON 的完整字段模版见 [contract-json-schemas.md](../contract-json-schemas.md) 第 1、3 节;返回的 `errors` 已是中文自然语言,直接说清哪里出错、怎么改,照着改产物即可(能否读校验器源码等规则统一见该文件抬头)。** `errors`(结构/禁止项/字幕矛盾等硬门)非零就直接改 Prompt 并重扫，不得凭回执自报的分数放行；`warnings`(Hook 证据/顺序等语义提示)不阻塞，逐条判断漏了补、等价说法则忽略，不为字面命中把好表达改生硬。

**`validate_final_prompt.py` 的硬门(`errors`)只有三项**:① 能否解析出带时间戳的分镜节拍；② 禁止词不得出现；③ 字幕指令不自相矛盾。**另有一类 `warnings`(提示、不阻塞 `ok`)**:当次用户选中 Hook 的身份性证据是否在开场窗和顺序中出现——只使用原始 Hook 派生的项目内证据、不使用全局关键词表，命中不了只提示、自查是漏写还是换了等价说法。其他首镜创意强度、单实例、主证明时长、尺寸真实与场景连续等仍由契约正文保证。多请求时每个 Prompt 的 `errors` 都清零后才能呈现给用户。

**编译前先跑卖点覆盖矩阵自校验（决策门阻塞项，硬性）**：按「卖点全覆盖合同」第 3 条，以「卖点账本」每条卖点为行、各镜号为列，依据内部 `shot_selling_point_map` 逐格核对该卖点是否被对应镜头的可见动作、结果或台词覆盖。**任何一条 P00 级卖点为全行未覆盖，必须停下询问用户**——补镜头覆盖，还是由用户明确拍板放弃（放弃才可豁免）；未经用户拍板不得静默进入生成。P0/P1 未覆盖项在面向用户的说明里点名列出。矩阵全部 P00 通过后，方可继续编译并呈现最终方案。

它必须涵盖：时长、比例、任务、标题；风格与视觉参考、镜头语言、视觉与美术规则、色彩与材质、打光、剪辑节奏、声音方向；场景、主体（品牌/产品/人物）；各分镜完整内容（拍法、画面内容、品牌/产品露出、声音，用从 `0s` 起的请求本地时间）；**每个用到参考图的场景/品牌/产品/主体都在其定义行内用 `对应@图片N` 声明绑定哪张图并写清只采用/不采用哪些维度，图序号 N 即执行时传入 `ImageList` 的位置（第 1 张=@图片1……），正文各分镜复用同一序号**；单请求时长边界（不披露模型名称）。

最终 Prompt 必须把第 3 步的 `融合创意规格` 编译为镜头内可执行指令，不能再次粘贴 Hook/Play/Style 原文，也不能让某个后处理步骤覆盖主创意。逐项反查：每个所选模板的传播职责、因果机制、标志性线索和用户锁定元素仍在，可观察落点仍在，Hook 末动作与专项主线/主证明首动作连续，Style 在各镜头使用同一套视觉语法。若拆成多请求，每个文件都携带同一份精简的 `商品真相 / 主 USP / 主专项说服机制 / Hook 职责与机制 / Play 机制 / Style 语法 / 主证明 / 场景路径 / 连续性不变量`；后续片段只推进状态，不重启注意力债务、不另起一条创意。

涉及人物时，最终 Prompt 不能只写“情绪从 A 到 B”或“做出某种表情”。每个关键人物节拍至少写出触发源、镜头可见的面部/呼吸/身体/手势或环境作用、人物当前行动意图、商品动作以及结果后的新反应，并让所选 Style 决定这些行为的真实度、幅度、速度与镜头距离。涉及奇观时同时写清奇观怎样实际改变主体或任务；禁止“奇观背景 + 主体状态正常 + 静态举品”。

编译 `视频生成Prompt.md` 时，必须显式声明素材角色边界：达人图只作人物形象参考，不作为商品参考；商品图只作产品外观参考，不采用人物/背景；产品形态、大小比例、使用方法、开合状态和卖点证明只能来自权威商品信息或用户补充素材。**若本次使用的产品参考图是 Agent 生成的（仅在用户强烈要求下才会发生），编译前必须确认：该图已经用户明确确认（注册表 `verify_status: confirmed`）、且正式绑进 `ImageList` 的是该产品的完整三视图（正+背+侧，必要时含顶/底/内部/使用状态），并在 `产品1：` 定义行里逐视角用 `对应@图片N` 声明；缺用户确认、或只传单角度生成图，即为阻塞项，回到第 5 步补齐。** 若是多图借鉴或局部修改，最终 prompt 必须逐项写清“基础图、目标对象/区域、keep/change/add/remove、每项来源、保留项、忽略项”，不得笼统写“参考多张图”或“融合风格”。改文字时必须写入用户确认的准确文字并锁定其它包装内容；动作依赖多状态图时必须按状态顺序绑定，不能让单张终态图承担完整动作路径。若提示词为了展示卖点需要虚构包装背面、侧面、配料表、内部内容、不合逻辑使用动作，或让不同参考图的未授权维度互相污染，判为不通过并回到脚本/素材阶段修改。

**编译时按核心契约把约束落成可核验结构，而非堆泛化文字**：① 按「产品真实形态与使用逻辑合同」从「商品模型」压出简短**商品尺寸台账**（`真实尺寸`/`可见比例`/`物态`/`source`），**并默认把尺寸内联编译进 `视频生成Prompt.md` 的 `产品1：` 定义行**——用可核验描述写清真实大小与画面可见比例（如「约一节 AA 电池大小、掌心可完全握住」），并在「全片连续一致性说明」锁定全片同一真实尺寸与相对比例，杜绝忽大忽小/整体失真；形态/部件/材质/颜色/文字/朝向等保真事实不再单列 match/否定表，通过 `产品1：` 定义行「只采用@图片N…、不采用…」采纳条款承载（避免与商品模型重复）；`source` 是内部追溯字段、不进 Prompt 正文。**尺寸未确定（`真实尺寸`=unknown 且未澄清）按「商品大小保障原则」阻塞，须先问清或按品类标准推导再编译。** 提交前逐条反向检查 Prompt 正文有无商品忽大忽小、可见比例与真实尺寸相悖、或与商品模型保真事实相反的描述，矛盾即阻塞；② 连续动作用**短状态机** `S0→动作(接触点/方向/受力)→S1→S2 + 全过程不变量` 表达，短·确定·可视，不过度分解，S0/S2 各绑状态参考图；有方向性/易穿帮商品的使用类分镜写明具名功能部位朝向；③ 按「参考素材台账合同」核对每个实体/状态单主锚点、逐图声明用途、`pending_derived` 素材未经确认不进 `ImageList`、同维度冲突已定唯一胜出图。

**每个视频请求都是独立的。** 整片能在一个请求内被当前运行时接受就只写一个文件；模型限制（时长、比例、任务类型、参考组合、不可避免的顺序依赖）迫使拆分时，才拆成 `视频生成Prompt-01.md`……文件数量与顺序须与实际视频调用一致，不为每个镜头/节拍/场景单独拆文件。需要视觉连贯且当前运行时一个请求做不完时，仅针对该依赖用尾帧衔接：在依赖文件里预分配未来尾帧路径（如 `assets/part-01-tail-frame.png`）标为待定，执行时先跑上游、提取最终帧到该路径、再以其作首帧参考跑依赖请求。

**拆分前先探查当前运行时的单请求最大时长。** 用可调用工具的 schema、运行时解析器、当前会话给出的显式能力应答，或环境信息 `The currently selected video generation model supports up to {{.max_video_duration}} seconds per request.`——绝不依赖存储在本 Skill 里的模型矩阵。向用户披露生成边界时，只说当前所选视频模型的**单请求最大生成时长，不披露所选视频模型名称**，并用面向用户的生产语言表达，例如：「每个请求最多支持 {{.max_video_duration}} 秒。确认方案在此边界内时我保持整片一次生成，只有视频工具要求时才拆分。」当运行时能在一个请求内接受所需时长、比例、任务类型与全部必要参考输入时，无论内部有多少镜头切换、场景、视角、节拍或主观内容密度，都只编译一个视频请求；只有当前运行时无法在一个请求内接受完整包（不支持的时长、比例、任务类型、参考组合，或不可避免的顺序依赖）时才拆分。不要把拆分当作简化超载创意或化解语音时间冲突的替代手段。

**先输出确认引导**（说清本次展示原因，如"这是可直接生成视频的完整方案，请你最终确认"；以及确认后会做什么，如"确认后我按此生成片段、按分镜顺序拼接并交付"），**再用 `present_sandbox_file`（`interrupt: false`）呈现 `视频生成Prompt.md`**（多文件先全部展示完），**随后调用 `dynamic_questionnaire` 收集用户是否同意执行**（确认 / 修改）。初始载荷字段、更早的同意、图像生成同意、隐藏方案，都不授权视频工作。

**这道门锚在 `sandbox_generate_video` 动作上，而不是"走到了第 6 步"——每一次 `sandbox_generate_video` 调用前都必须先经过它。** 真实故障：用户给了一份写死的完整镜头脚本（场景/人物/动作台词/氛围/音频/时长/比例全齐），Agent 便判定"单镜头直出"，把商品建模、故事脚本、`视频生成Prompt.md` 及其校验、本确认门整条工作流全部一次性跳过，台账直接写 `阶段: generate` 就冲 `sandbox_generate_video` 出片。**杜绝此路径：用户给了完整脚本/分镜、或 Agent 自认"直出/一镜到底/无需拆分"，都不豁免**——仍须把用户脚本编译成 `视频生成Prompt.md`、过 `validate_final_prompt.py`、再呈现并收「确认/修改」，用户确认后才允许调用 `sandbox_generate_video`。"输入已经很完整"只影响编译工作量，不改变必须过门这一事实。

**进入「最终方案确认门」前，未闭合的取证缺口一律先行拦截（硬性，本步高频漏放）。** 「最终方案确认门」（呈现 `视频生成Prompt.md` + 问「确认 / 修改」）**不是**用来兜住取证缺口的地方——绝不允许在「立体结构充分性子门 / 商品完整视图 / 使用方式 / 商品大小」仍判 `unknown` 且未向用户交涉的情况下，跳过补素材问卷、直接抛一个泛化的"确认此方案 / 需要修改"最终问卷给用户。只要生成前方案检查里存在任一未闭合的阻塞项，正确动作是**先发对应的补素材/澄清问卷**（按「关键信息保守收集合同」与「动态表单合同」补图/补素材默认项规则，把"上传真实图片/视频"作为建议方向、不预选文字兜底），拿到用户答复（补素材、或明确拍板降级/放弃）后，才允许编译并呈现最终方案。**「最终方案确认门」默认假定所有取证缺口已闭合；带着未闭合的 P00 结构/视图缺口进入该门，即为本步阻塞项，检查不通过。** 换言之：一个案例若识别出了 P00 立体结构存疑，却没有向用户要过侧面/斜 45° 图就走到了"确认此方案"，属于错误路径。
