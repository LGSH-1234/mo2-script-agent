
# 工作流 · 修改路由（贯穿全程）

> 本文件是「修改路由」的权威正文，贯穿全程。用户提出任何修改时即时读取。

## 修改路由（贯穿全程）

用户改动时，把修改路由到**最早受影响**的 Markdown 产物，更新并重新呈现受影响的需确认产物再次确认，然后从那里继续。**一旦改动涉及靠前步骤，其后所有下游产物都要重跑**（例如用户改了故事脚本，最终生成信息必须重新编译并再次呈现给用户确认）。

### 修改影响推导（硬性）

收到任何一条修改指令后，**在动手前先显式推导它会波及哪些「已经存在」的产物**，然后按依赖顺序对这些已存在的产物统一使用最新要求更新，绝不静默改一处、留其它旧版不动。

推导范围（按依赖顺序）覆盖但不限于：

- `营销脑图.md`（内部营销脑图，如已生成）
- `故事脚本.md`（故事脚本，如已生成/已确认）
- `视频生成Prompt.md` / `视频生成Prompt-XX.md`（最终生成信息，如已生成/已确认）
- 已生成的关键参考素材图（角色/达人形象、商品形象、场景图、关键帧构图等）
- 已生成的中间视频片段与拼接成片（如已产出）

推导步骤：

1. **定位改动源头**：先判断这次改动的最早归属方（事实 → 输入；说服/商品角色 → `营销脑图.md`；故事/分镜/文案/时序 → `故事脚本.md`；提示词/模型/请求/拼接 → `视频生成Prompt-XX.md`；素材外观 → 素材完整性检查里的对话结论 + 已生成的素材图）。
2. **沿依赖链向下枚举**：从源头出发，依次列出下游**已经存在**的产物有哪些、每一份会被影响的具体内容是什么（如"角色服装从白衬衫改成黑西装"→ `营销脑图.md` 中的核心创意/角色设定字段、`故事脚本.md` 中提到该角色的每一个分镜画面描述、`视频生成Prompt.md` 中「主体」段落与各分镜「画面内容/品牌·产品露出」、已生成的该角色参考素材图都要重做）。
3. **只处理已存在的产物，不超前产出后面流程的产物**：如果下游某个产物尚未创建（例如故事脚本还没写、`视频生成Prompt.md` 根本没写过；或素材图还没生成），**不要因为收到修改指令就提前把它做出来**——按现有工作流走到该步时再产出，届时自然会用最新要求。修改动作只作用于当前时点已经存在的那部分产物。
4. **统一采用最新要求**：对每一份被枚举出来的已存在产物，用当前累计后的最新要求（包含本次修改）就地更新，禁止出现"故事脚本按新版、最终生成信息还留旧版"的分裂状态。
5. **披露并按现有确认机制重新走确认门**：向用户简短说明「本次改动会同步更新哪些已存在的产物，因为它们都依赖被改的那一层」。`故事脚本.md` 若受影响就地更新，重新展示给用户过目后继续；`视频生成Prompt.md` 若受影响，按「呈现文件让用户确认的机制」（`present_sandbox_file` 以 `interrupt: false` 展示 + `dynamic_questionnaire` 收集同意）重新确认。素材图按素材完整性检查里的机制重新展示确认。
6. **对已生成的素材图/成片**：若外观/身份/服装/场景等改动会让旧素材图与新故事脚本不一致，说明冲突并询问用户是重新生成对应素材图（走第 5 步生成规则，包括默认比例）还是继续沿用旧图；对已渲染的成片，按修改路由末尾的重生成/重拼接规则处理。

**关键约束再强调一遍**：只对**当前时点已经存在**的产物做同步更新；尚未存在的下游产物不因修改指令而被提前产出，仍按原工作流在其所属步骤按最新要求自然生成。

### 「只改这里，别的不动」= 真·局部修改（硬性）

当用户说「只把 X 改成 Y，其它保持不变」时，这是一条**有边界的局部修改**指令，必须被真正当成局部修改来执行，绝不能借「重新生成」把没被点名的部分一起改掉。收到这类指令先把它拆成五项，再动手：

- **修改目标**：精确到镜头 / 人物 / 产品 / 局部区域——到底改的是哪一处。
- **允许变化项**：本次唯一被授权改变的维度（颜色、某句台词、某个部件、背景等）。
- **明确锁定项**：所有未被点名的维度——构图、其它实体、其它镜头、时长、比例、身份、其它文字，全部锁死不动。
- **必须原样继承的原调用资产与 Prompt**：原来那次调用用到的 `ImageList` 素材、图序号绑定、以及 `视频生成Prompt.md` 里未受影响的段落，都要逐字沿用，不重排、不改指、不顺手重写。
- **修改前后非目标区域一致性检查**：产出后比对非目标区域是否与修改前一致；发现被动了却没被授权，判为回归，回滚重做。

**工具能力诚实（硬性）**：如果当前运行时的编辑能力只能**整段重生**（无法做真正的区域级局部编辑），就**不许把它伪装成「局部修改」**给用户——必须明确告知「这次只能整段重新生成，非目标区域可能发生变化」的风险，并给出更稳的路径：**先用关键帧 / 首末帧锁住要保留的画面再重生，或先请用户确认接受整段重生**。用户认可后再执行，绝不静默地拿整段重生冒充无损局部改。有边界的编辑/延展/关键帧/AI 处理的具体契约见[素材与执行](../base/assets-and-execution.md)。

**默认在原文件上就地修改，不新增文件**（见「修改时的文件复用原则」）。只有当原文件结构无法承载修改结果时（如时长增加导致单请求容量放不下、须多拆一次调用），才在复用原文件的前提下最小化地新增；能收敛回单文件时则合并删除多余分片。

- 意图变化：重建营销方向（第 2 步）及全部下游。
- Hook/Style/Play 模块变化：重跑 Hook/Style/Play 编译（第 3 步）及下游。
- 故事或 Play 变化：保留输入真相，重建创意内容（第 4 步）及下游。
- Style 变化：保留故事，重建视觉体系、受影响素材、分镜处理与提示词。
- 镜头、文案或转场变化：保留上游创意含义，只重算受影响的节拍与请求。
- 同方案重新生成：仅当无任何内容或运行时字段变化时，才复用已确认的请求文件。
- 仅拼接变化：可行时重新排序、用 `render_video` 加字幕或混 BGM，不重新生成内容。
- 既有视频请求与交付后更改：用[素材与执行](../base/assets-and-execution.md)的既有视频章节。

用简洁、有意义的状态让用户了解进展，不叙述内部实现。
