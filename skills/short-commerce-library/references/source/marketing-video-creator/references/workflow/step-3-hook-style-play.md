
# 工作流 · 第 3 步：编译 Hook、Style 和 Play

> 本文件是第 3 步的权威正文。进入本步时即时读取。

## 3. 编译 Hook、Style 和 Play

### 3.0 用户未提供 Hook 时自动搜索补齐（前置）

**进入本步先判定用户本次创作是否已带 Hook。** 判据:第 1 步盘点(`references/workflow/step-1-intake.md`)里是否存在任何 GUI 或文本形式的 Hook——包括用户明确点名的 Hook 模板、Hook 提示词,以及用户成型口播/锁定脚本里本就承载了开场留存机制的开篇。**只要存在任一形式的 Hook,就跳过本小节、直接按下文正常编译,不要额外搜索、不要覆盖用户已选的 Hook。**

**当且仅当用户本次创作完全没有使用 Hook 时**,调用 `pippit_omni_search` 为其检索一个合适的 Hook:

- 入参 `SearchType` **固定传 `marketing_hook`,不可改**:无视工具签名/文档里为该字段暴露的任何其它可选值或枚举——无论工具声明它还支持什么类型,本链路一律只传 `marketing_hook`,不得按情境改传别的值,也不得让模型自行从暴露的选项里挑。检索关键词从已建立的事实底座(商品模型、主打卖点、目标人群情境、平台/时长)提炼,让返回的 Hook 与本商品和受众压力相关,而非泛搜。
- 把工具返回的结果**当作本次创作的 Hook 纳入编译**:与用户已选的 Play/Style 一起走下文正常的模板适配编译流程(拆 `机制不变量/表层变量/商品绑定/可观察落点/成功标准`、按角色联合编译、`adaptive_fusion` 等),受同样的商品事实、安全与平台约束,并同样进入第 3 步末尾的 8 项阻塞检查。搜索得到的 Hook 不因"是系统检索的"而豁免任何合同或校验。
- 面向用户仍只说人话结论(例如"我为这条视频挑了一个开场留存点子…"),不暴露工具名、`SearchType` 枚举或检索机制;把选定的 Hook 写进 `营销脑图.md` 的「创意方向」,并在台账登记本步已补齐 Hook。
- **搜到的 Hook 同样要落 `hook_acceptance_contract`,但 `selection_source` 填 `agent_selected`(不是 `user_selected`)**:把检索返回的 Hook 标识、名称与原始文案按原样写进 `hook_id`/`hook_name`/`original_prompt`,再照常派生 `signature_requirements` 等验收项。`user_selected` 这个值只留给用户自己明确点选的 Hook——两者不可混填,否则「不得用默认值覆盖用户明选 Hook」这道门就失去判据。本小节只在"用户完全没带 Hook"时触发,因此不存在覆盖用户选择的情形。
- **允许无结果,这是正常情形、不是故障**:`pippit_omni_search` 不一定有匹配数据——没有匹配时它不会返回内容。**返回为空就直接忽略、照常继续本步流程**,不重试、不报错、不因此阻塞,也不必强行自建或塞进一个 Hook;此时就当本次没有额外 Hook,按用户已有的 Play/Style 与事实底座正常编译即可,并在台账记录"未取到外部 Hook、继续"。仅当工具调用本身报错(而非正常空返回)时才可至多重试 3 次。

只要存在任何 GUI 或文本形式的 Hook(含上文 3.0 自动补齐得到的)、创意/Play、Style，就读[创意与分镜](../base/creative-and-storyboard.md)并生成一份内部 `融合创意规格`（该文件约 548 行，按「全局文件读取设置」读到末尾再动手）。**本步编译 Hook/Play/Style 的权威规则在根级 `contract-creative-and-script.md`，候选能否进入脚本的说服质量门在根级 `contract-persuasion-quality.md`；进入本步前必须把这两份文件均读到末尾。** **禁止把用户 Prompt、Hook Prompt、Play Prompt、Style Prompt 依次拼接或各分配一段时间。**它们必须共同作用于同一条商品因果链。

先建立唯一事实底座：`用户目标与锁定文案 + 商品模型 + 卖点账本 + 图片可见特征 + 主专项创意引擎 + 主证明 + 时长/平台/安全限制`。图片只授权可见的形、色、材质、结构和文字，不授权推断隐藏结构、真实用法或功效。任何适配前，先把用户选中的 Hook ID、名称和原始 Prompt 按原样写入 `hook_acceptance_contract`，随后为每个所选模板拆出：

- `传播职责`：用户选择后必须保留的注意力、叙事或视听任务；
- `因果机制`：触发、升级与结果怎样发生，必须保留；
- `身份性验收项`：去掉就不再是该 Hook 的动作、声源、构图、状态变化或顺序，保留对应原文片段、开场截止时间和可验收字面证据；
- `实现变量`：地点、景别数量、色彩、布景及不承担模板身份的普通道具，默认按商品与专项重写；
- `用户锁定元素`：只有用户明确要求照做、不能改或顺序固定的元素；
- `商品绑定`：该机制具体绑定哪条受众压力、卖点、使用动作或证明；
- `可观察落点`：它会改变哪个镜头、动作、声音、构图、剪辑或状态变化；
- `成功标准`：移除该模板后，成片必须出现可观察差异。

按角色联合编译：Hook 负责在第一拍提出与商品有关的问题、反差、结果或信息缺口；创意/Play 负责从第一拍开始组织叙事、动作与证明路径；Style 作为全片统一的视听生产语法。**Hook 的最后一个动作必须同时是 Play/证明链的第一个动作**，bridge 是这一个动作的延续或解释，不是另加一段过场。默认不让人物首帧举商品口播，除非商品揭示本身就是所选 Hook 的机制。

随后完成 `adaptive_fusion`：先写当前 SKU 的 `product_specific_tension / opening_state / product_causal_action / proof_state / end_state`，再分别写每个已选 Hook、Play、Style 对具体镜头造成的 `module_observable_effects`。若人物承担 Hook、叙事、口播或体验职责，再写 `human_performance`，把心理状态翻译成触发源、可观察行为、行动意图、环境作用、发声方式和结果反应；不得只写“生气、嫌弃、认真、释然、自信微笑”等情绪标签。若无人脸或纯商品，则用物体、环境和任务状态完成同一条状态链，不为过检查强加人物。

先定主证明，生成至少三个内容程序候选，自动淘汰 SKU/素材/Hook 闭环/时长/平台执行不合格者，再从合格候选找能自然提出主证明问题的 Hook。不授权未核实功效。**每个候选还必须按 `contract-persuasion-quality.md` 做商品替换测试和证明闭环检查：换成普通同类后至少两处关键环节必须需要重写；主证明必须有前态、商品动作、同一对象上的可观察变化与结果。只写包装、口播、幻想特效或人物反应的不算证明。功能型硬件/耐用品若只展示外观、配色、旋转、悬浮或走秀而没有功能动作、用户任务结果与具体利益点，直接重选；用户明确要求 N 个 SKU/款式时，候选必须规划覆盖至少 N 个可区分对象。**

选中候选后必须写清内部 `hook_question / product_action / proof_answer_shot`。主证明镜头必须使用当前同一 SKU 完成 Hook 所承诺的同一任务；商品形态、功能部位、使用方式、作用目标或素材证据任一不支持，就判 0 分重选，不能换成邻近任务蒙混过关。若 Hook 使用奇观、强环境力或超现实空间，还须写 `spectacle_causality`：奇观怎样作用到人物/物体/任务、造成什么商品相关状态、怎样触发行动并交接主证明；只有背景替换而主体状态不变，直接判为奇观摆拍。启用抖音/TikTok 时，再按平台执行底线的八项原生感标准自动评分；任一项为 0 或低于阈值，重写首屏、镜头密度、人物观看关系、动作声与收尾，不请用户做普通质量筛选。

把以上决定整理为内部 JSON，并在进入第 4 步前运行 `python3 scripts/validate_creative_contract.py <contract.json>`。校验除原有 SKU、Hook、融合、平台与本地化字段外，**必须包含 `persuasion_quality_contract` 与 `quality_acceptance_contract`**：锁定输入完整性、商品专属性、证明闭环、情绪因果、新鲜机制、证据承接 CTA，以及下一步对实际故事脚本要查找的项目内字面证据。`hook_acceptance_contract` 必须保留原始 Hook 来源、至少一项核心开场要求及冲突处理状态；未解决冲突或 UI 默认值覆盖用户明选 Hook 都不得通过。**完整字段模版见 [contract-json-schemas.md](../contract-json-schemas.md) 第 1 节。**注意本校验器的合同**只接受文件路径或 stdin**，不像另两个校验器那样支持内联 JSON。 返回非零或 `ok: false` 时按错误信息自动重选/重写并重新校验,不得忽略结果,也不得把普通纠错交给用户。临时 JSON 只用于校验，不作为交付产物。

场景按 `information_job` 编排：20 秒及以内优先一个主世界。`A→B→C→D` 可在每场新增不同且必要的购买理由、证明或信息职责时成立，并共享同一 USP、商品识别和连续动作/声音/构图线索。重复职责的换景必须合并。`A→B→A` 只有在回到 A 完成此前埋下的因果回报、主证明或关系改变时成立；只为重复背景、静态定格或“高级感呼应”而回访必须删除。用户锁定首尾回环时仍须新增可见验证。

冲突按 `事实与安全 > 用户明确硬约束/锁定文案 > 主证明可成立性 > 主专项说服机制 > 模板传播职责与因果机制 > 身份性线索 > 图片启发 > 实现变量/UI 默认` 裁决。先做**等强改写**：可改地点、普通道具、景别或语气，但必须同时保住原机制、身份线索、开场位置和商品因果，不得静默删除任一所选模板。UI 默认推荐永远不能覆盖用户明选 Hook。只有机制确实互斥、等强改写仍无法兼容时，才向用户提出一个最小问题。

进入第 4 步前先通过结构化合同，再做 9 项阻塞检查，每项 0–2 分：首屏停留、Hook 机制保真、商品专属性、目标人群命中、Hook→专项/Play 桥接、主证明有效、Play 落地、Style 全片一致、动态状态因果。任一项为 0 或总分低于 15/18，先重写，不生成故事脚本。**不得用“字段填满”代替质量判断：若商品替换测试、动作—变化—结果、证据触发的情绪转折或证据承接 CTA 任一不成立，即使总分自评达标也仍然阻塞。**
