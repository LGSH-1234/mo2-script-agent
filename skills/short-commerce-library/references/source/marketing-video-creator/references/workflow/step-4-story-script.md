
# 工作流 · 第 4 步：产出故事脚本（中间产物，写好即展示）

> 本文件是第 4 步的权威正文。进入本步时即时读取。

## 4. 产出故事脚本（中间产物，写好即展示）

处理 Hook/Style/Play、故事、通用形式、视听设计、分镜与实体状态时，读[创意与分镜](../base/creative-and-storyboard.md)——这是本步的功能主参考。**本步同时受根级 `contract-creative-and-script.md` 与 `contract-persuasion-quality.md` 约束；进入本步前必须把两份合同读到末尾。** 按第 2 步选定的方向创意文件、第 3 步编译出的 Hook/Style/Play 及已通过的说服质量合同组织故事脚本内容。

在落脚本前，由主专项创意引擎内部提出 3 个机制不同的候选：至少改变说服机制、商品专项角色、主证明、人物关系、世界规则或视觉构造中的一项；只换人物名、场景名或台词措辞不算。按该方向文件的退出标准选择最佳一个，再与第 3 步 `融合创意规格` 合并。候选只有在会造成实质方向选择且置信度不足时才展示给用户。

- 沿用第 3 步的 `融合创意规格`：用户所选机制必须保留且各有可观察落点；Hook、Play 与 Style 共同落在同一条商品因果链和同一组分镜中，不再回到各模板原 Prompt 分别扩写。若有已选 Hook，必须将第 3 步原样的 `hook_acceptance_contract` 带入本步，不在写脚本时第二次简化。
- 逐镜继承 `adaptive_fusion` 的状态变化。人物出镜时，画面描述写清“什么触发了什么可见行为、人物为何采取商品动作、结果出现后状态怎样变化”；不把抽象情绪词当作表演指令。无人脸时写清物体/环境/任务的前态、作用与后态。
- 逐镜落实 `persuasion_quality_contract`：先让观众看见顾虑或前态，再看见当前商品的具体动作、同一对象上的变化和结果；人物判断、关系变化与 CTA 必须发生在证明之后。包装、口播、幻想特效和无依据的惊讶反应均不能替代主证明。
- `functional_durable_goods_guard.applicable=true` 时，实际分镜必须分别出现功能动作、同一任务的可观察结果和具体用户利益；外观奇观只能辅助，不能替代。用户明确要求 N 个 SKU/颜色/款式时，脚本必须能逐项或按可区分数量验收到至少 N 个，禁止用“多款闪过”模糊带过。
- 写完先做同类替换测试：把商品名替换成普通同类后，如果 Hook、关键动作、证明、结局和 CTA 基本不用改，说明仍是模板植入，返回第 3 步重选机制。
- 按成熟度处理：`intent_only` 创建方向/故事/脚本；`story_provided` 保留所提供故事，只补营销因果、商品证明、文案与执行空白；`storyboard_provided` 除非要求不重写故事或视觉，只补缺失的营销/事实/时间/执行；固定文案除非授权原样保留。
- **用户提供的成型口播按「用户口播意图保真合同」当锁定文案处理**：其完整意图与核心信息必须落进故事脚本的「对白·旁白」列，不为凑时长擅自删改；若完整承载所需时长超过用户选定时长，先按该合同给出方案一(完整版)/方案二(精简版)让用户选，选定后再落故事脚本，不静默砍内容也不静默拉长。
- **台词如实登记（见「台词如实登记合同」）**：有台词（口播/旁白/对白/达人讲述）的镜头必须把台词内联写进「对白·旁白」列、不得漏记或藏进画面描述；但不是每个镜头都要有台词，纯画面/无人声/纯音乐的镜头该列留空即可，不为凑而硬加。写完自检：有人说话却没落台词的镜头即补齐后再展示。
- **分镜并入故事脚本，随本次一并写完。** 复杂多请求任务可用独立分镜规划器提方案，但根 Skill 必须规范化、协调、披露并拥有它。

故事连贯到可以讲清楚（主体、推进、商品/品牌角色、证明、结尾）后，按 `故事脚本.md` 冻结格式编写（字段级正文见 [frozen-formats.md](../base/frozen-formats.md)「故事脚本格式」，直接读该小节即可，不必整读 intake）。**画面描述列必须按「卖点全覆盖合同」第 2 条，在内部勾稽每条卖点到真正呈现它的画面动作上；面向用户的脚本不显示库编号或内部勾稽编号。**

**实际故事脚本是本步唯一真相源（硬性阻塞）**：每次新写或修改 `故事脚本.md` 后、任何展示或下游编译之前，必须运行 `python3 scripts/validate_story_script.py 故事脚本.md --contract <内部合同.json>`，直接扫描实际 Markdown。内部合同必须带 `duration_seconds`、第 3 步原样的 `quality_acceptance_contract`；有已选 Hook 时还必须带原样的 `hook_acceptance_contract`。**因此本步的 `--contract` 不可省略；合同含这些对象时体积较大，用文件路径写法（`--contract <项目>/_internal/story_contract.json`）而不是内联 JSON**（`--contract` 两种写法都被支持，仅 `duration_seconds` 这类极短合同才适合内联，写法与判定规则见 [contract-json-schemas.md](../contract-json-schemas.md) 第 0 节）。若返回 `--contract 指定的文件不存在`，那是**路径问题、不是产物问题**——注意相对路径相对当前工作目录（`cd` 进 skill 目录后就找不到项目目录下的合同了），跨目录一律用绝对路径；不要因此去读校验器源码反推字段。**完整字段模版见 [contract-json-schemas.md](../contract-json-schemas.md) 第 2 节。**

校验器返回分两类，处理方式不同：
- **`errors`（硬门，`ok:false` 阻塞）**：只覆盖能被字符串/结构可靠判定、正确产物一定能过的项——标题与唯一 8 列分镜表、表头分隔行、每行列数、时长格式、总时长对齐、内部工作流标签泄漏、混入多余段落。返回非零或 `ok:false` 时，按错误信息直接改写**同一个**故事脚本并重跑，直到 `ok:true`；不得展示失败版本。
- **`warnings`（提示，不阻塞）**：Hook 证据词、说服质量证据词（商品动作/可观察结果/改变后的结局/CTA 等）、证据出现顺序——这些是"你在第 3 步合同里承诺过、但脚本里没逐字照面"的语义点。**逐字命中与否属于语义判断，不作硬门**（否则会逼你为迁就词表把好句子改生硬、反复空转）。收到 warnings 时**逐条判断**：确属漏写了该证据/环节，就补进对应分镜；只是换了等价说法（如"裤袋"对"口袋"、"长发被风吹起"对"头发被风吹动"），就忽略该提示，**不要为了字面命中而改写已经写好的表达**。`ok:true` 即可展示与推进，warnings 不阻断，但也别无视——它是防止"合同吹了、脚本没落地"的最后一道自查。

不得只修改合同去迎合现有脚本，也不得用第 3 步创意合同的自报通过代替实际脚本通过。

校验通过后，若 `production_task` 为 `script_only / creative_only`，直接在对话中交付脚本，或用 `present_sandbox_file` 展示 `故事脚本.md` 后结束任务；不进入第 5、6、7 步。其它任务中，故事脚本是承接第 5、6 步的中间产物：用 `present_sandbox_file`（`type: text`、`interrupt: false`）展示给用户过目，正文里说明这是接下来素材与最终方案的基础、有意见随时可提，然后直接进第 5 步。用户此时若提出修改，就地更新 `故事脚本.md`，重新运行成品校验，通过后再展示并继续。用户真正拍板的确认门只在第 6 步的最终方案，故事脚本先展示、再继续即可。
