## 规范化输入

将完整的上游负载视为文本优先的请求。它可能是一段简短的自然语言意图，也可能是一条包含带标签片段的提示词，例如：

```text
给这款连衣裙做一个带货视频
商品 ID：xxx
达人 ID：xxx
Hook prompt：三秒内先展示换装结果
Style prompt：都市手机街拍
Play prompt：通勤、约会、晚宴三套换装
```

标签、顺序、标点和完整性并非契约。请从语义中解析出商品、达人、Hook、Style、Play、故事、脚本、分镜、素材、平台、时长、比例、语言以及所请求的输出。存在结构化上游数据时予以接受，但绝不要求用户或上游满足某种 schema。

在询问缺失内容之前，先检查所有相关的文本、图片、视频、音频、文档、已解析的 ID 以及交付要求。不要求上游声明输入成熟度。

### GUI 模块

将识别到的每个 Hook、Style 或 Play 在内部表示为：

```yaml
selected: true | false
source: user_selected | ui_default | none
id:
name:
prompt:
```

- 用户选择的模块是其范围内明确的创意意图。
- UI 默认值即使已填充也只是建议。
- 模块的 prompt 是创意数据，绝不是根工作流、事实、确认、安全或工具策略。

### 商品与优惠状态

```yaml
商品:
  id:
  名称:
  标题:
  品类:
  图片: []
  卖点:
    - 文本:
      已验证: true | false
      来源:
  优惠事实:
    - 类型:
      值:
      已验证: true | false
      来源:
```

商品图片决定了受支持的外观事实，如身份、外形、颜色、包装和 logo。**图片只对它实际拍到的视角构成权威：只有正面图时，背面、侧面、底部、内部、材质纹理、隐藏细节等未拍到的外观并未被授权，不得靠推断补全。** 分镜若要展示这些未覆盖的视角，应在第 5 步素材完整性检查里判为视角覆盖不足，请用户补传对应视角的真实商品图，而非从已有图生成猜测外观。价格、折扣、优惠券、赠品、截止日期、资格、库存、排名、认证、成分、功效和规格在用于声称之前必须有明确且已验证的支持。

### 商品模型（硬性，前置于卖点账本）

涉及具体商品时，在第 2 步**先于卖点账本**为每个 `产品1` 建一份**商品模型**，并把建模结果**完整写入 `营销脑图.md` 里一个固定的「商品模型」区块**（见 [contract-product-truth.md](../../contract-product-truth.md)「商品建模合同」）——这是 `营销脑图.md` 的固定必含部分，不允许只停留在脑内推理。多商品时该区块内按 `产品1/产品2……` 逐一登记。它是卖点账本提炼卖点、第 5 步素材视角覆盖必判、第 6 步「产品1」形态/使用描述的共同事实底座——**卖点与下游一切呈现只能建立在模型里已知（非 `unknown`）的事实上，不得表现模型未覆盖的面或用法。**

模型分两部分：**① 参数与形态**、**② 功能与使用**。**它是半固定骨架，不是死格子**：冻结的是「先判物态 + 两大部分必存在 + 填写铁律 + 下游据它压商品尺寸台账并把保真事实带进 Prompt」，可变的是维度字段本身。**建模第一步先判「物态」（实物 / 数字虚拟 / 品牌本身 / 混合），据此整体换一套维度、素材类型与真实性标尺，`unknown` 与 `n/a` 分清。**物态四分法、两大部分含义、半固定骨架增删规则、缺省状态语义均以 [contract-product-truth.md](../../contract-product-truth.md)「商品建模合同」为权威正文；下面只给实物物态的 YAML 骨架起点，其它物态按合同整体替换维度。

    材质: | unknown | n/a

  物态:                      # 实物 | 数字/虚拟 | 品牌本身 | 混合（第一步先判，决定下面整套维度、素材类型与真实性标尺）

      正面: | unknown | n/a         # 主视觉、Logo、屏幕、按键、开口等
      侧面: | unknown | n/a         # 接口、卡扣、厚度轮廓等
      顶部: | unknown | n/a         # 盖子、泵头、出料口、散热孔、铭牌等
      底部: | unknown | n/a         # 支脚、铭牌、开孔等
      背面: | unknown | n/a         # 仅当有权威素材支持时才写

    颜色款式SKU: | unknown | n/a
    # —— 品类特有维度（按需增补，字段名自拟，别硬塞进上面的通用名）——
    # 服饰：版型廓形 / 垂坠感 / 上身效果 / 面料克重 / 领型袖型 / 弹力……
    # 食品：口味 / 口感 / 香气 / 份量 / 保质期 / 包装形态……
    # 3C 数码：屏幕规格 / 接口 / 指示灯 / 按键布局 / 续航……
  功能与使用:                # ② 说明白正确用法、避免错误使用。同样按品类取用、增删、改名；适用却缺→unknown，品类不适用→n/a

    工作原理: | unknown | n/a       # 靠什么机制生效

    操作部件:                       # 逐个登记关键交互部件的作用；无此类部件→整项 n/a
      - 部件: | unknown             # 某按钮/旋钮/开关/接口/卡扣
        作用: | unknown             # 它是干什么的、怎么触发、有什么反馈
    标准使用流程: | unknown | n/a    # 从起始到完成的动作顺序，含接触点、受力方向、内容物流向、使用终点

    # 涉及使用动作的实物商品，本组「打开启动方式/操作部件/标准使用流程」是「商品使用方式保障原则」的卡点依据：

    # —— 品类特有维度（按需增补）——
    # 服饰：穿搭场景 / 搭配建议 / 洗护方式……   食品：食用方式 / 冲泡步骤 / 建议温度……

  # ===== 物态=数字/虚拟 时，把上面两大部分整体换成下面这套（外观分面/材质/手持/物理动作整类 n/a）=====
  形态与呈现(数字):           # ① 让人在脑中还原这个数字产品「长什么样、怎么呈现」；绝不脑补 UI

    使用角色与场景: | unknown | n/a  # 谁在用（管理员/操作员/店长）、在什么业务场景用
    接入/开通/有效期: | unknown | n/a # 如何开通、部署方式、周期/有效期

      优先索取: 商品图/短视频 | 演示视频 | 多状态图 | 界面截图/录屏 | 产品文档/功能列表 | 品牌VI/Logo源文件 | 文字描述   # 按物态选证据类型
      状态: 待问 | 已豁免 | 已补齐 | AI 推导补全   # AI 推导补全=用户要求自行生成、已提醒一致性风险

字段填写铁律（与骨架直接耦合的两条在此，其余通用铁律以 [contract-product-truth.md](../../contract-product-truth.md)「商品建模合同」为权威正文）：

- **当前 SKU 先于品类总信息**：用户介绍同一品类的多个款式/材质/用法，而商品图或当前商品字段只对应一款时，只把确定属于该款的事实放入当前 SKU；其余放入“其它品类选项非当前 SKU”。下游候选、脚本和 Prompt 只能消费当前 SKU 锁，不得把邻近变体的材质、长度、功能或用法并进来。
- **尺寸数值不自动转生活物件类比**：已有精确数值时优先写数值与真实人手/身体参照；只有用户提供或严格尺寸相符时才写物件类比。类比与已知尺寸明显冲突即阻塞。

其余通用铁律（先判物态再判品类、`unknown`/`n/a` 分清、只填权威来源已支持的、素材只对实际展示到的内容构成权威、形态与功能不互相倒推、用户表述 > Caption 机读、缺口按物态索取证据且文字默认不作外观/使用置信点、用户要求 AI 自行生成时的一致性提醒、模型随素材更新）均见上述权威正文，此处不重复。

### 卖点账本（硬性）

涉及具体商品时，在第 2 步把上面「卖点」/「优惠事实」归一化成一份**卖点账本**，写进 `营销脑图.md`。**它只能从先建好的「商品模型」里已知（非 `unknown`）的事实中提炼**——不得把模型标 `unknown` 的形态或用法写成卖点。这是第 4 步内部 `shot_selling_point_map` 与第 6 步卖点覆盖矩阵自校验的唯一依据。

**账本的目标不是把商品拆成尽可能多的原子卖点，而是替这支视频挑出少数几个真正值得花篇幅打的核心卖点。** 卖点做加法是本能，做减法才是专业——卖点越多，每个能分到的篇幅越少，最重要的信息反而被稀释，最后观众一个都没记住。所以账本要做两件事：先把商品事实**按主题收拢**，再从收拢后的主题里**排出主次、分配篇幅**。

```yaml
卖点账本:
  本条内容预算:
    duration_seconds:
    主打卖点数: 1
    支撑卖点数:
    其它信息节拍数:
    已激活卖点编号: []
    延后到后续选题的卖点编号: []
  主打卖点:                  # 整片的消费主线 / USP，有且仅有 1 条
    编号: USP
    内容:                    # 一句话讲清「谁、为什么非买它不可」，通常是最强的差异点或购买理由
    支撑事实: []             # 引用下面核心卖点里的编号，说明这条主线靠哪些事实站住
    来源: 商品系统 | 用户上传 | 已锁定文案
    已验证: true | false
  核心卖点:                  # 候选池；本条实际激活数量由 [contract-platform-and-execution.md](../../contract-platform-and-execution.md)「时长—卖点—信息节拍预算」决定
    - 编号: 卖点#1           # 稳定编号，全流程不变
      主题:                  # 一个收拢后的主题，如「外观设计」「材质做工」「收纳便携」「使用场景」「规格/SKU」
      内容:                  # 该主题下所有相关事实收在一起：如「白/黑/卡其三色 + Oversized 廓形 + 落肩剪裁」而非拆成三条
      优先级: P00 | P0 | P1  # P00=核心卖点(须落镜)，P0=重要，P1=增强
      篇幅权重: 高 | 中 | 低   # 越核心越该多给镜头/时长，用来指导第 4 步分配，不是平均罗列
      SKU:                   # 该主题涉及的 SKU（单 SKU 时可统一标注）
      来源: 商品系统 | 用户上传 | 已锁定文案
      已验证: true | false
      覆盖状态: 待覆盖 | 已覆盖 | 已豁免   # 覆盖矩阵校验时回填；「已豁免」须用户明确拍板
  关键事实清单:              # 不单独成卖点、但一旦出现在成片里就必须准确的硬事实（颜色/尺码/材质/规格/价格优惠等）
    - 事实:                  # 如「均码 S-XL」「100% 亚麻」「限时 5 折」
      归属: 卖点#N | 主打卖点  # 挂靠到哪条核心卖点下呈现；没有归属的可挂「关键事实」自身
      来源: 商品系统 | 用户上传 | 已锁定文案
      已验证: true | false
      状态: 已知 | unknown
```

字段填写铁律：

- **先收拢，再排序，最后按时长激活。** 把同一主题下的事实并进一条：所有外观相关（颜色、款式、廓形、剪裁）收成「外观设计」一条，所有材质/工艺收成「材质做工」一条，收纳/便携/容量收成「收纳便携」一条，依此类推。账本可以保存候选池，但**本条已激活卖点数必须遵守 [contract-platform-and-execution.md](../../contract-platform-and-execution.md)「时长—卖点—信息节拍预算」**：9–15 秒默认 1 条主打、最多 1 条支撑；未激活条目转入后续选题，不得挤进脚本或覆盖矩阵。
- **主打卖点有且仅有 1 条**：它是整片的消费主线，第 4 步要给它最重的篇幅，其余核心卖点围绕它做支撑，绝不平均用力。
- **篇幅按优先级递减分配**：`P00`+`高权重` 拿最多镜头与时长，`P0`/`中` 次之，`P1`/`低` 点到为止。第 4 步据此排镜，第 6 步据此校验，**都不再要求"每个原子事实各占一个镜头"**。
- **关键事实不等于核心卖点**：颜色、尺码、材质、规格、价格优惠这类硬事实，除非本身就是主打差异点，否则不各自升格成一条核心卖点，而是收进「关键事实清单」、挂靠到某条核心卖点下顺带呈现。它们的作用是"出现时必须准"，不是"每条都要单独拍一镜"。
- **每个「内容」「事实」必须直接来自权威商品信息**（商品系统解析数据、用户上传素材/文案、已锁定文案）；**禁止推断、禁止臆造、禁止用「通常/一般/应该」补全**。权威信息里没有的，留空并把该项标 `unknown`，绝不用编造值填充。收拢是把已知事实归类，不是拿主题名去脑补不存在的细节。
- **P00 判定**：用户明确点名要覆盖的、构成主要购买理由或差异点的、商品标题/主图直接主打的卖点，判为 P00。**用户点名的特定元素（某特定款式、某特定主张，如"Oversized""Jesus 相关"）一律至少 P00**——即便它被收进了某条主题卖点里，也要在该条的「内容」里显式列出、并保证第 6 步能校验到它有可见/可听落点，不能因为"收拢"而把用户点名的东西糊掉。
- 账本随商品信息或用户指令变化而更新，是修改路由里 `营销脑图.md` 层的组成部分。

### 素材注册表

```yaml
asset_id:
type: image | video | audio | document
asset_ref:
origin: user_upload | product_system | creator_system | campaign_system | gui_module | agent_generated
role: product_reference | creator_identity_reference | character_reference | outfit_reference | style_reference | scene_reference | storyboard_reference | video_reference | script_document | screenshot | product_card | unknown
linked_entity_id:
reference_lock: locked_by_user | unlocked_reference | agent_generated | n/a
locale_fit: matched | user_locked_override | mismatch | unknown | n/a
authority_scope: full_product | base_source | shape_structure | color_material | text_label | component_detail | state_content | scene_composition | visual_style | view_detail | usage_motion | identity | unknown
authority_tier: root_truth | pending_derived        # 用户上传/商品系统/达人系统=root_truth；Agent 搜索/生成/衍生=pending_derived
is_primary_anchor: true | false                       # 该实体+该状态+该用途下是否为唯一主锚点；非主锚点须在 note 写明额外补什么
state: closed | open | in_use | used | n/a            # 该图对应产品的哪个状态
used_in_shots: []                                     # 被哪些镜号使用
conflict_winner_dims: []                              # 与其它图在这些维度冲突时，本图为胜出方（其余图对应维度记入 ignore）
verify_status: confirmed | pending                    # pending_derived 未经对照检查或用户确认前保持 pending，禁止进入 ImageList
edit_operation: keep | change | add | remove | reference_only | unknown
target_region:
sequence_index:
preserve: []
ignore: []
note:                                                 # 非主锚点必填：本图额外补的视角/状态/局部/SKU
```

**单主锚点与逐图声明（硬性）**：每个实体（`产品1`/`主体1`/`场景1`……）、每个需区分的状态，在同一用途上只允许一张 `is_primary_anchor: true`。除主锚点外的每张同类图都必须在 `note` 写清它**额外补什么**（某视角/某状态/某局部/某 SKU），不允许几张同类图无角色地一起进 `ImageList` 让模型自选。**没有明确 `linked_entity_id` + `authority_scope` 声明的图一律不进 `ImageList`。**

**根真值 vs 待确认衍生（硬性）**：`user_upload`/`product_system`/`creator_system`/`campaign_system` 来源标 `authority_tier: root_truth`；`agent_generated`（含 Agent 搜索、生成、从其它图衍生）一律标 `pending_derived`。`pending_derived` 素材 `verify_status` 默认 `pending`，**未经第 5 步生成图像质量自检的逐面比对且用户确认、或用户明确认可，禁止升级为视频生成参考**——不得进 `ImageList`、不得充当商品外观/身份/尺寸权威。升级通过后才置 `verify_status: confirmed`。凭正面图脑补的背面图、搜来的近似商品图都属 `pending_derived`，默认不得当真值。**承载商品外观真值的产品图默认不由 Agent 生成（见 [contract-assets-and-localization.md](../../contract-assets-and-localization.md)「禁止 Agent 自行生成产品图合同」）；仅在用户强烈要求下才生成，且生成图升级为 `confirmed` 必须经用户明确确认（Agent 自检不替代用户确认），正式调用视频模型时须传入完整三视图（正+背+侧，必要面补齐），每个视角各登记一条注册表记录并绑定 `产品1`。分镜示意图（`role: storyboard_reference`）、关键帧图不受此产品图生成禁止约束。**

**冲突裁决**：多张图在同一维度给出不同信息时，为该维度指定唯一 `conflict_winner_dims`，其余图把该维度记入 `ignore`；不得把冲突图一起喂进去让模型平均取舍。

使用稳定的请求本地 ID。在赋予权限之前先检查相关媒体。商品照片的背景并不会自动成为所请求的成片风格。仅将参考视频作为用户所请求维度上的权威。在生成之前将远程 URL 解析为运行时可访问的素材，否则报告该阻塞点。

素材角色必须互斥清晰：`creator_identity_reference` 只授权人物五官、发型、妆容、体型、服装风格、姿态、表情、气质和人设；它不授权任何商品、包装、Logo、商品卡、购物袋、货架、背景物或手持道具作为 `产品1`。`product_reference` 只授权商品实际可见的外观面、形态、颜色、包装/Logo/标签位置、数量、大小比例和已确认状态；它不授权人物、服装、背景或未拍到的背面/侧面/内部内容。每个素材都要填写 `authority_scope`、`preserve` 与 `ignore`，防止跨素材误绑定。

当用户基于一张图借鉴其它图修改商品时，不要把所有图片都登记为 `full_product`。先登记一张 `authority_scope: base_source` 的基础图，再按实际任务把其它来源拆为 `shape_structure`、`color_material`、`text_label`、`component_detail`、`state_content`、`scene_composition` 或 `visual_style`。每项修改均填写 `edit_operation`、`target_region`、`preserve` 与 `ignore`；未被列入 `change/add/remove` 的基础图维度默认 `keep`。目标文字以用户明确文本或已验证字段为权威，图片中文字不可辨认时不得猜写。若映射不清，给 2-3 个贴合当前素材的组合选项并允许自由描述，未明确前不编译最终 Prompt。

动作或使用方式的证据按时间信息量登记：视频使用 `authority_scope: usage_motion`；多张状态图使用 `authority_scope: state_content` 并按 `sequence_index` 排序，至少区分起始、接触、中间和完成状态。状态图可约束每个关键状态及接触位置，但不得自行推断受力方向、速度、轨迹、停顿或内容物流向——这些运动细节的权威依据是使用演示视频（`usage_motion`）或走完「使用方式保障原则·证据升级阶梯」后用户确认的用法；**用户的纯文字说明默认不构成运动/使用方式的权威依据，不能仅凭一段文字就把状态图之间的动作补全为已知事实**（须按证据升级阶梯要求视频，未取得前使用方式维度保持 `unknown`）。单张完成状态图只授权完成状态，不授权完整打开/使用动作；但可直接用于“产品已经处于该状态”的镜头，不需要仅为解释此前动作而询问用户。

## 权限范围界定

在每个范围内应用权限：

1. 明确的用户文本和用户选择的 GUI 模块控制所请求的含义和创意约束。
2. 已验证的商品、活动和达人系统控制它们各自的事实。
3. 权威素材控制它们在画面中可见地支持的身份与外观。
4. 提供的固定脚本在锁定时控制措辞与顺序。
5. UI 默认值和参考基调只是建议。
6. Agent 推断填补缺失的创意决策，但不会因此成为已验证的事实；系统生成/搜索的人物身份默认未锁定，必须服从已确定的目标市场本地化。

当同一范围内两个高权限来源发生冲突时，披露该冲突并请求做出最小必要的决策。

商品卖点、产品外观和使用方法各自独立取证、只写各自权威来源已支持的内容：卖点以权威文本或可见素材为准，外观各面以对应参考图为准，打开/使用方式以参考视频或按顺序的多状态图为准。三者不能互相倒推：没有权威文本或可见素材支持的卖点不得写成事实；没有参考图支持的背面、侧面、配料表、内部内容、容量规格、认证和标签不得生成；没有参考视频、按顺序的多状态图或清晰结构支持的打开/使用方式不得强行演示。先诊断具体缺口，并先判断是否能不改变用户意图地改成素材支持的静态状态、已知视角或低风险展示；能改则直接继续，不追问。只有用户明确要求完整动作、核心证明依赖动作，或降级会改变用户意图时才请求证据：缺静态事实优先对应角度/细节/状态参考图，缺连续路径优先参考视频，也可请求起始到完成的多状态图和文字顺序。

## 输入成熟度与任务

设定：

- `intent_only`：存在目标、商品、达人、Style、Hook、Play 或前提，但没有连贯可执行的推进。
- `story_provided`：存在故事或脚本，但时间安排、可见节拍、镜头、绑定关系或连续性不完整。
- `storyboard_provided`：有序或定时的节拍已充分定义可见动作，足以用于生成。

在创意路由之前先确定 `production_task`：

- `generate`：创建新视频；
- `edit`：在改变某个有界元素的同时保留现有视频；
- `extend`：在现有片段之前或之后续接；
- `keyframe`：用首帧或首末帧约束运动；
- `process`：增强或移除某个视觉元素；
- `assemble`：拼接、加字幕或混入所提供的音频而不重新生成内容；
- `creative_only`：仅创意、故事、脚本、分镜或提示词。

保留现有视频的请求优先于新的创意构建进行路由。

## Markdown 产物

对于简单的一轮式仅创意工作，对话式输出可能已经足够。当工作进入生产链条、跨越多个步骤、需要用户确认或将驱动媒体生成时，创建一个专用目录：

```text
video-projects/YYYYMMDD-HHMM-short-slug/
```

**沙箱内 md 文件受严格限制。** 除生成的素材媒体（图片、音频、视频）外，理论上只允许存在以下三类 Markdown 产物，禁止再写入任何其它 md（不得创建 `storyboard.md`、`script.md`、`asset-plan.md`、`generation-plan/request-XX.md`、`execution-package.md` 或任何临时说明/索引文件）：

```text
营销脑图.md            # 内部营销脑图，非确认产物，不强制向用户呈现
故事脚本.md           # 故事脚本（含分镜），中间产物，写好即展示给用户过目，严格按 frozen-formats.md 故事脚本格式
视频生成Prompt.md  # 最终生成信息确认（唯一阻塞确认门）：最终生成信息 = 可直投视频模型的完整 Prompt
                          # 多次调用时拆为 视频生成Prompt-01.md、-02.md……
```

产物职责：

- `营销脑图.md`：**内部**产物，不是必须确认的产物。承载需求理解、营销方向、受众、主要价值、核心创意、Hook 到正片的过渡、故事主线、**商品模型（见上，涉及具体商品时先于卖点账本建）**、**卖点账本（见上，涉及具体商品时必建）**、已确认输入以及待解决问题。用于 Agent 自身推理与追溯，不强制向用户呈现。它采用 [frozen-formats.md](frozen-formats.md)「营销脑图格式」定义的**半固定骨架**：标题骨架必含、`商品模型`/`卖点账本` 两个区块冻结为固定 YAML，其余推理区内容自由展开。
- `故事脚本.md`：**故事脚本（中间产物，写好即展示）**。合并旧 `script.md` 与 `storyboard.md` 的用户可见内容。故事脚本本身即包含分镜，写完后作为承接素材检查与最终方案的基础，用 `present_sandbox_file`（`interrupt: false`）展示给用户过目、有意见随时提，然后直接进入素材完整性检查。严格按 [frozen-formats.md](frozen-formats.md)「故事脚本格式」。
- `视频生成Prompt.md`：**最终生成信息确认（唯一必须阻塞的确认产物）**。合并旧 `generation-plan/request-XX.md` 与 `execution-package.md`。它是**可直接投喂视频生成模型（Seedance）的完整 Prompt**，严格按 [frozen-formats.md](frozen-formats.md)「最终生成信息格式」。**禁止修改其字段定义或结构**：必须保持可被视频模型直接消费。每个视频请求都是独立的，若整片需要多次调用视频模型，则拆为 `视频生成Prompt-01.md`、`视频生成Prompt-02.md`……每个文件都是一段完整、请求本地（从 `0s` 开始）的 Prompt，数量与顺序和实际视频调用一致。

三个产物的字段级冻结格式（`营销脑图格式` / `故事脚本格式` / `最终生成信息格式`）的唯一权威正文见 [Markdown 产物冻结格式](frozen-formats.md)。第 4 步写 `故事脚本.md`、第 6 步写 `视频生成Prompt.md` 时直接读该文件对应小节。

不要维护内部的机器状态文件或执行守卫。当前的 Markdown 产物加上对话确认即是工作流记录。

当某个产物需要用户确认时（**唯一必须确认的文件是 `视频生成Prompt.md`**），Agent 必须呈现实际文件，而不是仅在对话中总结它。**确认门的完整交互纪律——固定顺序（先输出确认引导 → `present_sandbox_file` 以 `interrupt: false` 展示 → `dynamic_questionnaire` 收集「确认 / 修改」）、引导必须写清的三要素、多个 `视频生成Prompt-XX.md` 的展示与问卷编排、修改后重走一遍、以及 `故事脚本.md` 作为中间产物只展示不阻塞——以 [collaboration-and-quality.md](collaboration-and-quality.md)「Markdown 产物」「强制视频决策门」为权威正文。**

不要仅为创意方向创建一个独立的 Markdown 文件。通过对话或 `dynamic_questionnaire` 确认方向（**使用 `dynamic_questionnaire` 时问卷只按真实候选出题，遵守 [contract-interaction-products-delivery.md](../../contract-interaction-products-delivery.md)「动态表单合同」**），然后在创建 `营销脑图.md` 或 `故事脚本.md` 时把所选或继承的方向记录在其中。

素材完整性检查（在故事脚本写好之后）在对话中完成，**不写入任何 md**：不创建 `asset-plan.md`；对缺失的角色/商品/场景素材，在对话里请用户上传或询问是否可由 Agent 生成。

## 确认继承

当范围内用户提供的内容足够清晰可执行时，将其视为已确认：

- 事实性选择，如商品、平台、时长、比例、语言、优惠或 CTA；
- 创意性选择，如方向、故事、场景顺序、固定脚本、Hook、Style、Play、角色或结尾；
- 用户明确要求保留的维度所对应的、所提供的分镜或参考材料。

不要要求用户重新确认他们已清晰提供的范围。继续推进到下一个缺失的生产层级，如分镜、素材方案、生成方案或执行包。

在以下情况下停下来确认：

- 缺失创意方向且 Agent 必须选择路由；
- Agent 新推断、改写、压缩、重排或实质性地解读了用户内容；
- 高权限来源发生冲突；
- 该层级将驱动下游素材、提示词、工具调用或最终执行；
- 之前确认过的 Markdown 产物被实质性地更改、替换或扩展；
- **缺失营销关键事实**（商品功能、尺寸/尺码、材质、颜色/款式、`P00` 核心卖点、价格优惠等），权威来源无法解析——此时**不许推断补全，必须向用户问清**（见 [contract-product-truth.md](../../contract-product-truth.md)「关键信息保守收集合同」）。

**关键事实的缺失尽量一次问齐，避免本可预见却拆成多轮的零散追问。** 在写 `故事脚本.md` 之前的输入规范化 / 建「卖点账本」阶段，就把所有标为 `unknown` 的关键事实汇总成一份待问清单向用户发问（**发问方式——默认统一走 `dynamic_questionnaire`、用点选代替打字降成本、及其唯一例外——以「关键信息保守收集合同」第 1 条为唯一权威，本节不复述**）；发问前先自检，能从权威来源、用户已给文案、可见商品图得到的不再问——**「外观」与「使用方式/场景」例外：这两类不因用户文案里描述过就算已答，纯文字不作其权威，仍须发问、要求图片/视频。**用户没答的关键项保持 `unknown` 待定，不得脑补后继续；用户明确说"不用放"才可把对应卖点标为「已豁免」。一次问齐是目标而非硬性——若用户回答后又暴露出新的、或后续步骤才浮现的关键缺口，允许再追加补问，好过带着 `unknown` 硬推。这属于前置澄清，不占用后面唯一的最终生成信息确认阻塞门。

在故事脚本写好之后、生成规划之前，当视频使用或可能需要角色/达人、商品或场景素材时，**在对话中执行素材完整性检查**：逐一盘点是否已有可用的权威素材，对缺失项请用户上传或询问是否可由 Agent 生成，二选一。在用户答复前把该素材保持待定，不静默生成、不静默跳过、不用不相关素材替代。此检查不落 md 文件。

当后续的视频部分依赖前一部分的末帧以保持连续性时，依赖它的 `视频生成Prompt-XX.md` 可以在该帧存在之前声明一条待生成的衍生素材路径。这条待生成路径必须稳定、位于同一项目目录之下，并被描述为将来源自上游输出的首帧/参考图片。上游视频完成后，在开始依赖请求之前将提取的帧保存到该路径。

每个 `视频生成Prompt-XX.md` 将评审上下文与运行时时间分开。诸如 `13-24s` 这样的整片区间可以出现在文件顶部的元信息或拼接上下文中，但供视频工具使用的完整 Prompt 正文必须从该请求的 `0s` 开始，并将所有定时动作、转换、台词、声音提示和结尾备注都保留在 `0-duration_seconds` 之内。不要把全局偏移带入 Prompt 正文。

唯一的确认门，确认目标是所呈现的 Markdown 文件（最终生成信息确认=`视频生成Prompt.md`）。对话文本可以引导用户，但被确认的产物是该文件。确认引导必须包含**本次展示的原因**和**确认后下一步会做什么**。`故事脚本.md` 作为中间产物可展示给用户过目，但不构成阻塞确认门。

在询问时，将已确认的输入与 Agent 填充的内容区分开：

```text
根据你的输入已确认：
- 时长：15 秒
- 故事：通勤 -> 约会 -> CTA

需要你确认：
- 我把这个故事翻译成了这份 4 节拍分镜。
```

## 修订归属

使用如下依赖顺序：

`input -> marketing/营销脑图 -> 故事脚本 (含分镜, 中间产物, 写好即展示) -> asset completeness check -> 视频生成Prompt (最终生成信息确认) -> merge -> delivery`

更改最早拥有该内容的产物，保留有效的上游工作，并更新或丢弃不再匹配的下游文件。如果 `故事脚本.md` 发生实质性更改，就地更新它并同步重编下游的 `视频生成Prompt.md`；如果已确认的 `视频生成Prompt.md` 发生实质性更改，在下游使用之前再次请求确认。**完整的修改影响推导、真·局部修改边界与依赖链重跑规则以[修改路由](../workflow/modification-routing.md)为唯一权威正文；本节只给依赖顺序概览。**

修改时默认**在原文件上就地修改，不新增文件**，仅当原文件结构无法承载时才在复用原文件的前提下最小化新增、可收敛时合并回单文件——**该「修改时的文件复用原则」的完整正文以[交互·产物·交付契约](../../contract-interaction-products-delivery.md)为唯一权威。**

对于状态报告，或已被确认的最终生成信息覆盖且未发生变化的拼接，无需新的确认。仅当没有任何内容、素材、运行时、提示词或拼接字段发生变化时，同方案的重新生成才能复用同一个已确认的 `视频生成Prompt-XX.md`。
