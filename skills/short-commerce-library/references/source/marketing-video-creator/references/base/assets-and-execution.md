
# 素材与执行

只复用或准备承载信息的素材，编译模型支持的请求，披露确切的执行，运行经对话确认的媒体操作，并处理有边界的编辑。

## 目录

- 中间素材
- 运行时能力探查
- 请求编译
- 参考素材绑定与请求数量
- 已有视频操作
- 披露与确认
- 执行、拼接与失败

## 中间素材

对每个候选项：

```yaml
asset_decision:
  decision_id:
  asset_type: image | voice_anchor | derived_frame | derived_tail
  action: reuse | generate | derive | skip
  information_role:
  source_asset_ids: []
  governed_entities: []
  downstream_segments: []
  preservation_scope: []
  reason:
```

默认采用 `reuse` 或 `skip`。只有当图像能够实质性地稳定原本脆弱的商品身份、达人/角色身份、已确认的穿搭状态、场景几何、关键构图、具体的 Style 信息、关键帧，或由能力所迫的多请求连贯性时，才生成图像。**承载商品身份/外观真值的产品图是硬性例外：默认不由 Agent 自行生成（见下「权威外观优先要真图」与 [contract-assets-and-localization.md](../../contract-assets-and-localization.md)「禁止 Agent 自行生成产品图合同」），只有在用户强烈要求下按强制流程（风险声明 → 生成 → 用户确认 → 完整三视图）才生成；分镜示意图、关键帧图不在此禁止内，但关键帧里的商品外观仍须取自已确认真图。**

定义主体与角色、权威绑定、身份不变量与允许的变化、下游取景、禁止臆造以及允许的消费方。对于商品，保留形状、颜色、logo、标签排布、材质、比例和 SKU。对于人物，定义角色、年龄段、面部/发型锚点、服装逻辑、姿态、气质、表情习惯、场景以及与商品的关系。

**人物素材图默认比例与商品隔离（硬性，权威正文见 [contract-assets-and-localization.md](../../contract-assets-and-localization.md)「商品素材与达人素材隔离合同」）：生成人物/角色/达人形象参考素材图时，若用户没有明确指定比例，一律默认使用 `3:4`。人物图只用于稳定人物五官、发型、体型、妆容、服装风格、姿态、气质和人设，不得带入营销商品、商品包装、商品同款道具、购物袋、货架、商品卡、Logo 牌或任何可能被误认为 `产品1` 的物体。** 仅当用户明确要求了其它比例、或该素材有明确的下游取景/关键帧构图需要另一比例时才偏离该默认；此默认只作用于人物素材图的生成，不改变整片视频的比例，也不覆盖商品、场景等其它类型素材各自的取景需要。

**人物图默认贴合目标市场、优先当地人特征（硬性，除非用户锁定人物）：生成达人/模特/角色/路人等人物形象图时，若人物未被用户锁定，默认按已确定的 `target_market / cast_localization` 优先采用目标市场当地人的可信特征**——面孔肤色、发型发色、体型、妆容取向、服装风格与气质表演都朝当地当代真实人群靠拢，而非默认西方面孔或与市场不符的长相（如泰国市场默认当代泰国人物、印尼市场默认印尼人物）；市场未明确但「单一当地语言 + 当地电商平台/购买路径」高度一致时，按本地化合同采用可修改的低风险默认值。只做自然、当代、真实的本地化，不用夸张民族服饰或刻板符号贴标签。用户已锁定人物参考时锁定优先、保持其身份不因市场默认改脸；生成后须核对人物特征与目标市场是否一致，不一致即重生成或换候选。

在故事脚本写好之后,只要商品、模特/人物或场景参考素材有意义,就在生成规划之前**在对话中执行素材完整性检查,不写入任何 md（不创建 `asset-plan.md`）**。依据故事脚本盘点每一个被引用的素材实体,对每个类别在对话里说明:

```text
参考素材类别（角色/达人、商品、场景等）：
是否需要：yes | no
已有素材：有（复用）| 无 | 不足以支撑其信息角色
覆盖是否充分（按物态判：实物类判视角/角度覆盖，数字类判界面/功能覆盖，品牌类判VI资产覆盖）：充分 | 不足（缺哪些）
缺失时如何处理（二选一，必须向用户交涉）：请用户上传 | 询问是否可由我生成
下游用途：
```

**多图借鉴与局部修改素材绑定（硬性）：** 当用户要基于一张图片修改商品并借鉴其它图片时，素材完整性检查必须明确「基础图」和逐项「修改维度权威」。修改维度包括外形结构、颜色材质、文字/Logo/标签、局部部件、开合或内容状态、数量组合、背景构图、光线和视觉风格。每项都写清目标对象/区域、`keep/change/add/remove`、采用来源、保留项与忽略项；未被点名修改的基础图内容默认保持不变。目标文字以用户明确文本或已验证商品字段为准，参考图只在清晰可辨时提供排版/字体/位置参考。若映射不清，给 2-3 个针对当前图片的组合选项并允许自由描述。禁止把参考图的拍摄角度、比例形变、背景、阴影、人物、结构或旧文字等未授权维度带入结果。

**素材覆盖充分性判断，按物态分轨（硬性）：** 「有一张图」不等于「素材充分」。判断标尺随商品模型的 `物态` 切换：
- **实物商品**：对照已确认故事脚本里各镜头**实际要展示的视角与细节**——正面、背面、侧面、顶/底、内部、材质/纹理特写、logo/标签、开合状态、不同颜色款式/SKU 等——逐一核对现有图能否可信支撑。若分镜需要某个视角而现有图（如只有正面图）看不到，判为**「不足以支撑其信息角色」**。**此外还要判「立体结构充分性」：当某 P00/主打卖点或用户点名的易错点本质是一种立体结构关系（部件一体还是独立、凹凸、层叠、连接方式、内外、开合等），而现有素材只有单一视角、该角度物理上无法证清这个结构（单看一张，"一体"和"独立"都说得通）时，即便"这个面已经拍到了"、即便"分镜根本不拍侧面特写"、即便"用户已用文字说清结构"、即便"该商品用法很直观/属于通用标准用法"，也判为「不足」，须向用户索取能看清该结构的多视角图（侧面/斜 45°/该结构特写），不得靠单张同角度图或用户文字描述当已知。详见 [contract-product-truth.md](../../contract-product-truth.md)「商品完整视图保障原则」的立体结构充分性子门。特别注意:「用法通用/通用标准用法」只免"要使用演示素材"这一项,绝不代表外观/尺寸/立体结构视图已充分——两道门相互独立,严禁用"用法直观→素材齐全"把结构视图缺口一并放过。**
- **数字/虚拟商品**：不判「视角覆盖」（外观视角整类 `n/a`），改判**界面/功能覆盖**——故事脚本要展示的每个界面/看板/功能路径/数据视图，现有截图/录屏/产品文档能否可信支撑；缺了某个页面就判「不足」，**绝不脑补 UI 补齐**。**不要向数字产品用户索取商品各角度实拍图或手持演示视频。**
- **品牌本身**：改判 **VI 资产覆盖**——片子要用到的 Logo/主色/标准字/代表性视觉元素是否都有官方素材支撑；缺了就判「不足」，**不得自造 VI**。

无论哪一类，判为「不足」都不得当作已齐备直接推进。

**权威外观优先要真图,不用生成猜测图（实物物态，硬性）：** 实物商品的真实外观是权威事实。当缺的是某个真实视角/细节(如只有正面、缺背面或鞋底或材质特写),**默认请用户补拍/补传该视角的真实商品图,而不是从已有图"生成"一张背面/细节图**——凭正面图脑补背面,本质是臆造未见过的外观,违反关键信息保守原则。**Agent 默认禁止自行生成承载商品外观真值的产品图**;仅当用户**强烈要求**、或该视角属于不承载权威商品事实的纯氛围/占位用途时,才可生成。用户强烈要求生成时,必须走强制流程(见 [contract-assets-and-localization.md](../../contract-assets-and-localization.md)「禁止 Agent 自行生成产品图合同」):①生成前先声明「自生成图可能与真实产品不一致」的风险;②生成后经用户明确确认(Agent 自检不替代用户确认)方可作参考;③正式调用视频生成模型时传入**完整三视图**(正+背+侧,必要面补齐),而非单张角度图。若用户既无法补图、又不同意生成,则调整分镜、回避该看不到的视角,而不是硬拍一个猜出来的外观。**数字/虚拟物态同理**：缺的界面默认请用户补传真实界面截图/录屏,不凭空生成一套 UI 冒充产品真容;**品牌物态同理**：缺的 VI 默认请用户补传官方 Logo/VI,不自造。

**商品卖点与外观不得互相虚构（硬性）：** 商品图只授权其实际可见的外观面、形态、比例、颜色、logo/标签位置和已看见文字；商品标题、用户文案或系统字段只授权其明确给出的卖点和事实。不得为了让卖点更可视化而生成未提供的背标、侧标、配料表、成分表、认证、规格、容量、口味、内部内容、剖面结构或附件；也不得从商品外观倒推未提供的功效、成分、规格、使用方法。脚本需要展示这些信息时，必须先请用户补充权威文本/商品图；无法补充时改为口播、场景结果、用户反应、对照体验或正面包装同框。

**产品形态、大小与使用物理检查（实物物态，硬性）：** 此检查针对 `物态: 实物` 的商品。每个涉及产品的动作都要核对产品形态和手持尺度是否匹配用户图。软袋、硬盒、瓶罐、管状、泵头、服饰、配件、电子产品等不能互相替换；不能让小物突然变大、盒装变瓶装、袋装变罐装、正面包装变成背面标签。拿起、递出、打开、按压、喷洒、涂抹、倒出、穿戴、安装、点击等动作必须有可见手/工具/接触点、运动方向和结果。现有素材无法确认动作路径时，默认先把分镜改成素材能证明的静态状态或低风险展示，不为此自动追问。只有用户明确要求完整动作、核心证明依赖动作，或降级会改变用户意图时，才优先请用户提供参考视频；也可请用户提供按顺序标注的未打开、接触、半开/中间和完成状态产品图，并说明受力方向与先后。单张终态图可直接用于终态展示，但不用于推导此前动作。**对于使用方式因设计/型号而异的非简单产品（非牙刷/发梳这类无使用歧义的产品），当用户要生成的视频确实涉及其使用动作时，按 [contract-product-truth.md](../../contract-product-truth.md)「商品使用方式保障原则」的证据升级阶梯硬性取证：①首选向用户要使用产品的参考视频（即便用户已用文字描述过用法/场景也仍须要视频）；②无视频可要求上传完整使用过程的顺序状态图；③视频、图片都拿不到、且用户在被要求补媒体后仍强烈坚持只用文字时，Agent 才可基于该文字推断一版文字使用方式，且必须显式声明「文字版控制力较弱」、交用户检查，用户确认后才写进 Prompt（用户未强烈坚持用文字、或未确认前 `使用方式` 保持 `unknown` 阻塞，不得进入 prompt 阶段）。文字对使用方式默认不作置信点。**

**数字/虚拟物态改走「界面真实性与流程一致性检查」（硬性）：** 对 `物态: 数字/虚拟` 的产品，不套上面的手部物理动作检查。改核对：画面里出现的界面/看板/图表是否与真实截图/录屏一致（布局、菜单、功能名、字段、数据视图），**绝不脑补 UI**；表达的「使用」是否为界面动作/数据流转/视图切换/流程节点推进（如入库→上架→拣货→出库→对账在看板上流动），而非硬安的实物手部动作；真人出镜操作电脑/手机时屏幕内容仍受上述界面约束。缺失的界面按上一条默认请用户补真实素材，不凭空生成。

**品牌物态改走「品牌视觉一致性检查」（硬性）：** 对 `物态: 品牌本身` 的片子，核对 Logo 造型/配色/留白/组合、品牌主色、标准字是否与官方 VI 一致，**不得改 Logo 比例配色、不得杜撰 slogan、不得自造 VI**；片中若出现具体产品，该产品回落到对应的实物或数字检查。

**达人图不得污染商品绑定（硬性，权威正文见 [contract-assets-and-localization.md](../../contract-assets-and-localization.md)「商品素材与达人素材隔离合同」）：** 在视频请求里，达人/人物图只能作为 `主体1/达人1` 的人物参考。**生成达人/人物形象图时默认白底（或纯净中性背景）、干净构图、只有人物本身——不带商品、包装、同款道具、购物袋、商品卡、货架、手持物，也不摆使用姿态、不搭建场景。** 达人图里的衣服、配饰、包、帽子、背景物、图案、手持物不得作为 `产品1` 使用，也不得替代用户商品图。若达人衣服本身就是被营销商品，必须由用户明确说明，并把它注册为商品素材或商品事实，否则按人物服装处理。**产品的拿放、使用方式与人货互动场景不在人物图里预置，全部由 `视频生成Prompt.md` 的分镜按已确认商品素材与商品模型控制，交给视频模型在生成时合成。**

不要在不告知的情况下擅自决定生成、上传、跳过或替换商品、模特/人物或场景参考素材。对每个缺失或不足的素材,必须在对话中显式二选一交涉——请用户上传,或询问是否可由我生成;在用户给出上传或"同意生成"的答复之前,禁止静默生成、静默跳过或用不相关素材替代。此检查在对话中完成,不落 md 文件。

在用户已就参考图像和 TTS 音色锚点确认(上传或同意生成)后,二者的具体生成动作无需再逐一征求同意。在有意义的生成之前,告诉用户正在稳定哪些信息。**每张图生成完成后,先由 Agent 自己逐张核验再决定去留(硬性)**:核查①崩坏/畸变(多手多指、肢体扭曲、五官错乱、结构断裂、文字乱码、AI 伪影、比例失真等)、②是否符合「商品模型」已知事实(形态、大小比例、颜色款式、材质、Logo/标签位置、可见面一致,不得臆造模型未覆盖的面)、③是否符合用户明确要求与素材约束(白底干净人像、无商品混入、比例正确、点名元素到位)。**任一不合格即定位问题、调整提示词重新生成,不得把崩坏或跑偏的图展示给用户或带入视频生成;同一张图重试到约 3 次仍不过,停下来向用户说明具体问题并给选项(换角度重试/补传参考图/调整分镜回避),不静默用坏图。** 自检通过后,再**对会实质影响成片的关键参考素材（角色/达人形象、商品外观、场景、关键帧），简要展示产出并请用户确认是否符合预期,通过后再进入视频生成**;次要或一次性、不影响成片的素材可径直使用。检查并登记实际结果的角色契合度,展示重要输出及其角色,并且在某个输出未能胜任其角色或用户提出修改时重新生成。

只有当稳定的重复出现的音色能实质性改善连贯性，且运行时接受音频参考时才使用 TTS。使用一句简短中性的目标语言句子。TTS 音色锚点不是完整的口播、旁白、达人说话、台词或 CTA 轨道。不要把 TTS 当作不受支持的音乐生成来用。

当 `sandbox_generate_video` 支持音频输出时，计划的口播、旁白、台词、达人说话、语气、停顿和时间归属于视频提示词内部，以便工具同时生成同步的音频和画面。不要创建一个由 agent 生成的 TTS 旁白文件再混入生成的视频，除非用户明确要求单独的 TTS 制作，或当前视频运行时无法生成所需的语音音频。

只有在源视频已存在且后续请求需要连贯性时，才派生尾帧或短尾片段。只将其绑定到有依赖关系的消费方。

### 尾帧衔接

只有当活动运行时无法在一个请求中完成整个方案，且相邻请求需要视觉连贯性时，才为多请求视频生成使用尾帧衔接。如果它是可选而非必需的，则在生成方案中建议它并等待用户确认。

在执行前规划该依赖：

```text
上游请求：视频生成Prompt-01.md
派生素材路径：video-projects/YYYYMMDD-HHMM-short-slug/assets/part-01-tail-frame.png
状态：待定,直到 part-01 的输出存在
下游请求：视频生成Prompt-02.md
下游职责：首帧参考图
```

下游的 `视频生成Prompt-XX.md` 可以在图像存在之前包含待生成的 derived asset 路径。明确说明它将从上游视频的最后一帧提取，并用作首帧/参考输入以保持连贯性。

该依赖的执行是串行的：

1. 执行上游视频请求。
2. 提取其最后一帧。
3. 将该帧保存到预先分配的待用路径。
4. 将保存的图像绑定进下游请求作为首帧/参考输入。
5. 执行下游请求。

当提取的帧仅履行已确认的连贯性衔接时，无需新的确认。只有当提取的帧实质性改变可见意图、替换了已确认的参考素材，或迫使提示词、素材、时长、比例或拼接发生变化时，才重新呈现受影响的生成方案。

## 运行时能力探查

从当前可调用的工具 schema、运行时解析器，或当前会话中可用的显式能力响应来解析能力。该快照是执行证据，而非维护的目录：

```yaml
runtime_capability_snapshot:
  source:
  resolved_at:
  max_video_duration:
  supported_task_types: []
  image_limit:
  video_limit:
  audio_limit:
  mixed_file_limit:
  supported_ratios: []
  supported_resolutions: []
  prompt_reference_syntax:
runtime_model_name:
```

不要在此 Skill 中存储模型/版本能力矩阵。绝不从显示标签推断运行时名称。只有在明确解析出来时才传入运行时名称；当选择由平台路由掌管时则省略。当运行时数据提供了时长、版本、比例、分辨率或参考数量限制时，绝不硬编码这些值。如果某个必需的能力无法解析，则在最终视频决策之前报告该不确定性，而不要臆造一个限制。

## 请求编译

为每个已确认的信息角色创建一个图像或短音色锚点请求，只使用受支持的字段。当视频请求可以直接承载语音音频时，不要为完整旁白创建音色请求。

编译每个视频请求：

```yaml
video_request:
  request_id:
  segment_id:
  task_type: auto | edit | extend | keyframe
  runtime_model_name:
  prompt:
  image_list: []
  video_list: []
  audio_list: []
  duration_seconds:
  aspect_ratio:
  resolution:
  dependency:
  UseRunPrompt: false
```

- `auto`:全新的文本/图像/参考生成；
- `edit`:包含源视频，并保留时长，除非另有支持；
- `extend`:包含源视频，并定义续接；
- `keyframe`:按受支持的顺序绑定已确认的首帧或首/末帧。

**硬性调用参数：任何时候调用 `sandbox_generate_video` 都必须显式将 `UseRunPrompt` 设置为 `false`。绝不能设置为 `true`；否则会导致严重灾难性后果。凭你的良心，任何时候都要记住这一点。**

每个提示词都必须在不读取内部状态的情况下可执行。包含任务、时长、比例、语言、权威实体与状态、音画基线、按顺序的定时节拍、镜头/动作、确切的台词/旁白/达人说话文本、语气、停顿、声音/文本策略、商品证明、Hook/Style/Play 要求、连贯性以及明确的素材角色。对于 `sandbox_generate_video` 的直接音画输出，提示词是语音音频生成的归属方。

每个提示词都必须使用请求本地时间。如果分镜或执行包将整片描述为 `0-13s`、`13-24s` 或类似形式，则在撰写完整提示词之前，把当前请求转换为从 `0s` 到 `duration_seconds` 的本地时间。请求元数据可以写 `full-film range: 13-24s`，但提示词正文应写"在本请求的 5s 处"或"5s 后"，而非"18s 后"；对于一个 11 秒的请求，它应在 `11s` 结束，而非 `24s`。这同样适用于场景切换、台词时间、声音提示、尾帧/关键帧续接以及最终转场备注。

当存在活动的 Hook 时，用明确的时间边界编译提示词，而非粘贴原始的 Hook 提示词。说明 Hook 注意力时间、Hook 到正片的过渡时间以及正片接管点。在正片接管点之后，提示词必须让商品信息、卖点、证明、使用流程、场景、CTA 或品牌记忆成为主要指令。在接管点之后，不要把 Hook 场景、Hook 环境、Hook 动作链或 Hook 氛围保留为主要视觉场景，除非用户明确要求以 Hook 主导的整体概念。

使用正向的保留指令。相较于装饰性细节，优先考虑用户需求、实体身份、核心动作、证明和台词。

只对受支持的、提供的音频、BGM 或运行时接受作为参考的短音色锚点使用 `audio_list`。不要为口播旁白默认规划"生成静音视频 -> 生成 TTS 旁白 -> 混音"的工作流。

## 参考素材绑定与请求数量

为每个文件定义实际可访问路径、信息角色、受管辖的实体/状态、提示词 token 或列表位置、允许的消费方以及必须保留的范围。**传入顺序必须与 `视频生成Prompt.md` 里的图序号一致：`@图片N` 的 N 即该图在 `ImageList` 的位置，按图序号从小到大、无缺位地依次传入；`@视频N`/`@音频N` 同理各按其列表顺序。** 只按披露的确切顺序传入被使用的文件。

一个生成片段等于一个视频请求；内部分镜节拍则不然。

先解析当前运行时能力：

- 如果时长、比例、任务类型和所有必需的参考输入能一起被支持，即使有很多场景、剪切、人物、商品或节拍，也编译一个请求；
- 只有当活动运行时无法在一个请求中接受该包时才拆分；
- 记录确切的不受支持能力；绝不以主观的复杂度或内容密度为由；
- 如果创意或语音使受支持的时长过载，则简化，或请用户修改时长/文案，而非分段。

**尽量把单次调用的时长用满到运行时上限窗口，以此把总调用段数压到最少（正向引导，不写死具体秒数）。** 单次 `sandbox_generate_video` 能装多长，以运行时能力快照解析出的 `max_video_duration` 为准（绝不硬编码 15s/30s 之类的固定值——不同模型上限不同）；内部分镜节拍再多也不等于要拆调用——多个短分镜只要总时长在单次上限内，就合进同一次调用一起出，而不是一镜一调用。例如脚本分成 3s + 4s + 6s 三个分镜、共 13s，而运行时单段上限有 15s 时，这三段应放在**同一次调用**里出（一个请求 13s），绝不拆成三次 3s/4s/6s 的调用。只有当总时长确实超过单次上限、能力所迫必须拆分时，才拆，并让段数尽量少（用满上限窗口，别无谓多切段）。**这只是段内时长分配偏好，不改变前四条**：能一个请求装下就绝不拆；拆分仍须是运行时能力所迫、不得以主观复杂度为由；也不得为了「凑满窗口」而把用户选定的整片时长拉长或注水内容——窗口打满只用于减少段数，不用于增加总时长。段与段的时间轴仍各自从 `0s` 开始本地计。

当使用由能力所迫的多个请求时，在呈现请求文件之前，将分镜的整片范围映射到每个请求各自的本地时间轴。下游请求可以包含一句话的上一片段摘要或首帧依赖，但新的定时指令必须从 `0s` 开始。

对于由能力所迫的多个请求，执行依赖轮次。如果计划的尾帧或尾视频仅解决一个已披露的运行时依赖，则在源完成后再绑定。如果已解决的依赖实质性改变可见内容，则重新呈现受影响的 Markdown 产物。

### 分镜图与商品多视图的合并（强制合并，硬性）

**只要出现多张分镜示意图或同一商品的多张视角参考图，就必须先用内置脚本 `scripts/merge_images_grid.py` 合并成少数几张「拼图大图」，再进入下游——这是硬性强制，不以「是否超单次调用图片上限」「用户是否明确要求」为前提。** 具体覆盖两个环节：①**分镜确认展示**——向用户 `present_sandbox_file` 呈现分镜图时，**默认合并成 1–N 张分镜总览拼图整体展示，禁止一张一张地逐张展示**；②**进入 `ImageList`**——分镜示意图或同一商品的多视角图要绑进视频生成的 `ImageList` 时，先合并成拼图再绑，**禁止**靠拆成更多视频请求、或静默丢弃部分图来硬凑。`sandbox_generate_video` 单次调用能接受的图片数量有运行时上限（由能力快照解析，不写死）；合并同时也是把 N 张图压进该上限的标准手段：

- **分镜图合并（`--mode storyboard`）**：把逐分镜的关键帧/示意图连同序号、时间、景别、节拍、画面动作/产品露出/镜头转场/声音/口播字段拼成故事版网格图；每格带 `01/02…` 序号，prompt 里用「@图片N 的第 X 格对应分镜 X」引用具体分镜。
- **商品多视角合并（`--mode product-views`）**：把同一商品的正/背/侧/顶底/内部/材质特写/使用状态等多张**真实**视角图拼成一张「多视图参考大图」；每格带视角标签，prompt 里用「@图片N 的『背面』格」引用具体视角。这正是「完整三视图」在图片超限时的承载方式——三视图/多视图合并成一两张拼图传入，而不是各占一个 ImageList 槽位。
- **按上限自动分页**：脚本 `--max-per-sheet` 按每张拼图最多容纳的格数自动切成 `<prefix>_1.png`、`<prefix>_2.png`……据当前运行时图片上限设定每片格数与拼图张数，保证合并后拼图总数 ≤ 单次调用图片上限；`--cols` 控制列数。
- **合并时机**：在第 5 步参考素材准备阶段完成合并——**既用于向用户 `present_sandbox_file` 分镜确认展示（默认展示合并后的总览拼图，不逐张展示）**，也用于随后进入第 6 步 prompt 编译前绑进 `ImageList`；合并后的拼图作为新的参考素材登记进注册表（记录它由哪些原图合并而来），并按图序号绑进 `ImageList`。**合并只是把多图打包成拼图，不改变任何图的信息角色与「只采用/不采用」采纳条款**：拼图里每格的采纳维度仍按原图各自的绑定条款在 prompt 里逐格声明。
- **调用示例**：
  - 分镜:`python3 scripts/merge_images_grid.py --mode storyboard --input <storyboard.json> --out-dir <assets_dir> --cols 3 --max-per-sheet <据上限设定>`
  - 多视图:`python3 scripts/merge_images_grid.py --mode product-views --input <product_views.json> --out-dir <assets_dir> --cols 3 --max-per-sheet <据上限设定>`
- **输入 JSON 结构（照此模板写 `--input` 文件，不必去读脚本源码）**：两种 `--mode` 各有固定字段；`tiles` 里每格的 `image` 必须是磁盘上已存在的真实图片路径（脚本会逐个校验，缺图直接报错退出）。**正式字段名是 `tiles` / `image` / `view` / `desc`；脚本对常见同义写法做了兼容归一**——顶层直接给数组等价于 `tiles`，列表键 `images`/`items`/`views`/`shots`/`list`、图片键 `path`/`file`/`src`、标签键 `label`/`name`/`title`、说明键 `note`/`description` 都会被自动归一并在 stderr 打 `WARN` 提示，出图不受影响；只有「一个格子都没有」或「某格没有任何图片路径」才报中文 `ERROR` 退出 2。**真实故障：曾把每格写成 `{path,label,note}` 并把列表键写成 `images`，导致 `AttributeError: 'list' object has no attribute 'get'` / `tiles 为空`，然后反复 `head`/`grep` 脚本源码反推字段——现在不会再失败，但仍请照正式字段名写。**`--cols`/`--max-per-sheet`/`--prefix`/`--font` 均可选，字体缺省时脚本自动找系统 CJK 字体。
  - `--mode storyboard`（分镜图合并）——`tiles` 每格对应一个分镜，字段除 `index`+`image` 外均可选：
    ```json
    {
      "title": "整条视频标题",
      "consistency": "角色与一致性（跨镜形象/音色锚点）",
      "visual_mood": "视觉与情绪：色调/光线/节奏",
      "tech_spec": "技术规格：分镜数/总时长/画幅/字幕策略",
      "tiles": [
        {
          "index": 1, "time_range": "00:00-00:02.5",
          "image": "assets/keyframe_1.png",
          "shot_size": "近景", "beat": "Hook 悬念提问",
          "action": "画面动作", "product": "产品露出",
          "transition": "镜头转场", "sound": "声音", "voiceover": "口播文案"
        }
      ]
    }
    ```
    （`consistency`/`visual_mood`/`tech_spec` 是末页底部的总结块，均可选。）
  - `--mode product-views`（商品多视角合并）——`tiles` 每格对应一个视角，`view`+`image` 必填、`desc` 可选：
    ```json
    {
      "title": "产品1 多视角参考",
      "product_id": "产品1",
      "note": "同一件商品的多张真实视角图，供视频模型统一参考外观真值",
      "tiles": [
        { "view": "正面", "image": "assets/p1_front.jpg", "desc": "Logo 居中，正标可读" },
        { "view": "背面", "image": "assets/p1_back.jpg",  "desc": "成分表 / 条码" },
        { "view": "侧面", "image": "assets/p1_side.jpg" }
      ]
    }
    ```
    （`note` 是末页底部说明块，可选。）
  - **输出**：脚本按 `--max-per-sheet` 自动分页，逐行打印生成的拼图路径 `<prefix>_1.png`、`<prefix>_2.png`……最后打印 `SHEETS=<页数>`；`--prefix` 缺省时 storyboard 用 `storyboard`、product-views 用 `product_views`。
- **强制合并、无豁免**：只要有多张分镜图或多张同商品视角图，就必须合并，**不存在「未超限即可逐张传入/逐张展示」的例外**。分镜确认阶段一律以合并后的总览拼图整体展示；仅当用户**明确要求**看单张原图时，才可在合并展示之外额外附上原图。合并后的拼图同样受第 5 步生成图像质量自检约束（崩坏/畸变、是否符合商品建模、是否满足用户要求）。

## 已有视频操作

在新的构建之前，先路由已有视频和交付后的请求。

### 保留与修改

对有边界的更改使用编辑或拼接：替换/移除/新增一个元素；在保留受支持的时间/运动的同时更改服装、颜色、背景或 Style；移除/重排整个片段；用 `render_video` 开关字幕；添加/移除提供的 BGM；提升分辨率；移除文字；或编辑一个受支持的区间。

编译：

```yaml
edit_contract:
  source_video_id:
  target_interval:
  keep: []
  change: []
  references: []
  expected_result:
```

只包含实际打算并受支持予以保留的属性。披露限制。

**「只改这里、别的不动」按真·局部修改处理（硬性）**：用户要求有边界的局部更改时，`edit_contract` 必须精确到修改目标（镜头/人物/产品/局部区域），`keep` 列出所有未被点名的锁定维度（构图、其它实体、其它镜头、时长、比例、身份、其它文字），`change` 只列唯一被授权的维度；原调用的 `references`（ImageList 素材、图序号绑定）与 `视频生成Prompt.md` 未受影响段落逐字沿用，不重排不改指。产出后比对非目标区域是否与修改前一致，被动却未授权即回滚重做。**若当前运行时的编辑能力只能整段重生、做不到区域级局部编辑，禁止把它伪装成「局部修改」**——如实告知「只能整段重生、非目标区域可能变化」的风险，先用关键帧/首末帧锁住要保留的画面再重生，或先请用户确认接受整段重生，用户认可后才执行。

### 重做

当被营销的主体、目标、故事、结尾、说服机制、大部分镜头、整体构建或内容主线的 Play 发生变化时，重建创意与下游工作。

用户反馈产品问题时，按“诊断 -> 判断能否直接修 -> 必要时补证据 -> 替代方案”处理。先基于原始商品素材、生成结果和脚本指出最可能出错的维度或动作节点；已有证据足够，或能在不改变用户意图的前提下改成已知状态/低风险镜头时，直接给精准修法并继续，不要求重复上传。只有保留完整外观或动作对用户意图、核心卖点或证明不可替代且现有证据不足时，才把补素材作为首选：静态问题上传对应角度/细节/正确版本/目标状态参考图；连续动作问题上传真实或近似参考视频，也可上传按顺序的起始、接触、中间、完成状态产品图并描述方向/顺序。同时给 1-2 个无需补素材的选项，如只保留已知视角、改准确文字、强化局部约束、已打开/已完成状态、静态展示+口播或结果对比，并允许用户自由描述。

### 延展

定义源片段、延展方向、确切的退出状态、新的动作/故事任务、时长、实体/音频连贯性，以及续接是无缝的还是刻意转场的。不要无缘由地重启开场或重置商品状态。

### 关键帧

只有在受支持时才使用已确认的或为此目的生成的首/末帧。定义运动路径；仅有帧并不能指定动作。

### 拼接与处理

仅拼接类操作包括重排/移除整段片段、拼接、用 `render_video` 开关字幕，或混入提供的整片 BGM。当这些已包含在已确认的执行包中时，无需新的视频确认。新请求的非生成性拼接可在简洁地披露范围后进行。

增强、可见文字移除或其他改变像素的 AI 处理需要完整的视频确认节点。保留未被改动的源，并披露对面部、商品标签、logo 或细节的风险。

在编辑、延展、关键帧或 AI 处理之前，展示源、区间/范围、KEEP、CHANGE、参考素材、确切提示词/请求、预期结果、限制和下游影响。

## 披露与确认

在视频生成、编辑、延展、关键帧或 AI 处理之前（最终生成信息确认）：

1. 运行生成前方案检查。
2. 把可直接投喂 Seedance 的完整方案编译进 `视频生成Prompt.md`（严格按 frozen-formats.md 的最终生成信息格式，禁止改其字段定义）。整片能被当前运行时一次接受时只写一个文件；能力所迫需要多次调用时，拆成 `视频生成Prompt-01.md`、`视频生成Prompt-02.md`……数量与顺序与实际视频调用一致。不要另写 `storyboard.md`、`asset-plan.md`、`generation-plan/request-XX.md` 或 `execution-package.md`。
3. **先在正文输出确认引导**，说明本次展示原因（如"这是可直接生成视频的完整方案，请你最终确认"）和确认后下一步（如"确认后我会按此方案生成视频片段、按分镜顺序拼接并交付成片"）。

6. 如果用户在问卷里选「需要修改」或写了改动,更新受影响的 `视频生成Prompt.md` 并再走一遍第 3-5 步；只有在用户于问卷中确认之后才继续。

## 执行、拼接与失败

在对话明确确认之后，每个请求先执行一次。若 SKILL.md 第 7 步的有限技术完整性审查确认商品增殖/消失、SKU 或部件漂移、严重手部/持握错误、物体穿透等确定性生成故障，则结果未能胜任其确认的信息角色：只重写受影响节拍并自动重试一次；第二次仍失败就披露故障并等待用户决定，不无限自动消耗额度。记录实际输入、输出、时间戳、状态和错误。

对于多个输出，按披露的分镜顺序拼接实际返回的视频路径。使用受支持的拼接能力进行拼接、混入提供的 BGM。**字幕后处理默认不自动做,成片产出后按"用户一开始是否要字幕"分两条问卷路径,均须解释原因并告知擦除扣积分、按 1 秒 1 积分(前提:AI 生成不稳定,模型可能违规把字幕烧进画面;字幕擦除会扣积分,擦除 N 秒扣 N 积分):路径 A——用户要求无字幕时,用 `dynamic_questionnaire` 只询问是否擦除可能被烧录的字幕(解释原因+告知扣积分 1 秒 1 积分),同意才用 `sandbox_process_video` 擦除、否则原样交付;路径 B——用户要求有字幕时,用 `dynamic_questionnaire` 给二选一「无需擦除,直接添加字幕」/「擦除视频异常生成的字幕,再添加字幕」,并解释 AI 生成字幕不稳定、烧录字幕与后期字幕直接叠加会重影,故可先擦(扣积分 1 秒 1 积分)再加,两选项最终都用 `render_video` 加字幕(文案取自 `故事脚本.md` 已确认的对白·旁白),选先擦再加时先擦后加。面向用户的问卷与说明只说"字幕擦除"与"扣积分(1 秒 1 积分)"即可。** 不要用 shell 媒体命令替代受支持的最终拼接。

在安全或权限被拒时，停下并说明可操作的原因。不要在不告知的情况下移除素材或削弱含义。在传输失败时，保留确切的已确认请求并报告失败的步骤。一次成功的调用并不代表用户接受内容;交付所生成的文件供用户审阅，**且一律通过 `present_sandbox_file` 呈现（不用正文贴路径或链接代替）**。

修改归属：

- 源更改 -> 输入及下游；
- 营销/故事/全局 Style/Play 更改 -> 归属的创意阶段(`营销脑图.md` / `故事脚本.md`)及下游；
- 特定镜头更改 -> 故事脚本(`故事脚本.md`,中间产物)中受影响的分镜就地更新,并同步受影响的 `视频生成Prompt.md`（后者变化时重新确认）；
- 仅拼接的顺序/字幕/BGM 更改 -> 仅拼接/交付；
- 完全相同方案的重新生成 -> 复用同一个已确认的 `视频生成Prompt.md`(或对应的 `视频生成Prompt-XX.md`)并追加执行结果。

当实际输出存在，且已确认的拼接、（经问卷路径决定并知悉扣积分后才做的）字幕擦除与后期加字幕、提供的 BGM 或打包操作完成时，标记交付完成。不要要求或声称进行了生成视频的质量检查。
