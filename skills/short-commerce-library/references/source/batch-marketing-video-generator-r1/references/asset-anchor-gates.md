
> **Node knowledge:** This reference defines visual consistency and semantic requirements for image requirements with product / character / scene / prop / style / derived-reference roles; PM determines which nodes are active and ready.

# Asset And Anchor Gates

Use this reference for visual product, character, scene, market-fit, paid-image, and product-state consistency gates. Speaking-role consultation and audio anchors belong to `voice-anchor-gates.md`; read that complete reference when resolving or changing a voice, not as a substitute for these visual rules.

### Resolution Authority

Apply the current declaration before the concrete-anchor rules below. A permitted auto or waived resolution requires explicit user_evidence and can close that creative material requirement without generating a file; it is not silent omission or a concrete reference. Apply the following generation/review rules when providing a concrete asset. Product coverage cannot be delegated or waived. Runtime continuity requirements remain separate: their concrete anchors cannot close with auto/waived.

### Paid Image Cost Contract

For a READY runtime anchor, first apply `runtime-anchor-contract.md`. Reuse an existing entity without regeneration or renewed subjective approval. With recorded `user_delegated` authority, materializing a continuity-only scene skips the subjective acceptance steps below, not market-fit, technical checks or spending authorization. With `user_review`, retain presentation and acceptance. This exception does not authorize new characters, redesigned environments or invented product facts.

Treat a usable user-provided product or entity image as the direct identity reference. **Never spend an image-generation call to create a separate baseline, canonical copy, clean redraw, isolated redraw, or same-state confirmation image for an entity the user already supplied.** Its background, pose, handling state, crop, or lack of alternate angles does not by itself authorize a generated replacement. Reuse the actual supplied media in storyboard and video requests; when a cleaner source is business-critical, ask the user for one or disclose the limitation instead of silently generating it. A user-confirmed supplementary product state reference is allowed only for a view or state that the confirmed story requires and the supplied media does not actually show, under the Product View And State Coverage Contract; it never replaces or redraws the supplied source.

Generate a canonical anchor only when no usable user-provided identity image exists and the workflow must establish a stable visual identity for later independent calls. The On-Screen Character Anchor Contract below makes this mandatory for every identifiable appearing character that lacks an image anchor, including a character the user described only in text. For other entities, generate only when a new consistency-critical identity is genuinely required. The first accepted generated image is that entity's baseline; do not generate another baseline for it. Before any such extra paid image call, explain what new anchor will be created, why existing media is insufficient, and confirm it through `dynamic_questionnaire`. Shot frames and necessary persistent altered-state references are separate outputs, not excuses to regenerate supplied product media as a baseline. If supplied media is corrupt, unreadable, or depicts the wrong entity, ask the user for a replacement; do not silently generate a substitute.

**Product consistency is the highest-priority visual requirement for every marketing video, independent of whether the user buys a visual storyboard.** After video_blueprint describes the products and planned visible states and video_spec_definition declares their image requirements, PM exposes their concrete product requirements and then `product_state_coverage/<project>/<video>`. Complete that typed coverage node before asking whether to generate `storyboard-grid-XX.png`, and before creating any per-video package. The visual-storyboard choice controls only storyboard-frame spending and review format; it never controls, postpones, or waives product consistency.

For required canonical entities other than characters/scenes, keep the baseline isolated, complete, and in its default state: a new product/package concept must not invent localization or product facts, and a recurring prop must not be precomposed into a story moment. Generate only identities needed by the confirmed current-round direction. Combine entities and temporary interactions in raw-frame generation; a persistent changed state belongs in a separately cost-confirmed derived reference. A prior raw frame or actual video end frame is continuity evidence, not a canonical identity baseline. If supplied media needs format or dimension adjustment, use deterministic non-generative conversion instead of a paid redraw, preserving its source and a new output path.

### Market Fit Contract For Generated Visual References

Use the current video's `video_blueprint/<project>/<video>.market_target` as the concrete target, together with upstream facts and constraints. The campaign-wide market list is a scope, not a substitute for this video's selection. Read `audience` as intended viewers, not a required character identity. An `unspecified` field does not authorize guessing; resolve it before work that materially depends on it. An accepted per-video choice or materialization correction belongs to its owner under `revision-routing.md`; do not change the entire campaign when only one video's specialization is wrong.

Before proposing or generating any visual anchor, read the accepted `information-understanding.md`, the selected video's confirmed direction, complete video_blueprint and video_spec_definition. Establish a compact market-fit scope containing the target country/region, target audience, placement platform when known, the entity's campaign role, and any confirmed cultural, climate, category, modesty, age-depiction, or regulatory constraint that materially affects visual design. Target language alone is not a substitute for target market. If the market or another factual material field is missing or ambiguous, resolve it through `dynamic_questionnaire` and revise its semantic owner under `revision-routing.md` before returning to the paid call; do not keep a newly learned market only in conversation. If a field genuinely does not affect this reference, state a concrete `not material` reason in the asset evidence rather than silently omitting the assessment.

Market fit is mandatory for every newly generated character anchor and applies to generated scene, prop, style, product-state, or derived references whenever their visual design can vary by market. Carry the applicable scope into the actual image prompt in concrete visual terms. For characters, use the role, audience, product category, and campaign tone to choose casting direction, age impression, presentation, grooming, wardrobe, styling, and commercial energy. For scenes and props, apply relevant architecture, household, retail, workplace, climate, cultural, and platform conventions without turning a reusable canonical environment into a shot-specific composition.

Do not infer ethnicity, skin tone, body type, religion, nationality, socioeconomic status, or traditional dress solely from a country/region label, and do not use caricatures or token stereotypes as localization. When those attributes materially affect the brief and are not explicitly established, present a non-stereotyped recommended direction and allow correction. Preserve every usable user-provided person, product, package, scene, and prop exactly as the authoritative identity; target-market adaptation never authorizes replacing a supplied person, changing product geometry or claims, translating packaging, inventing a localized SKU, or generating a second baseline. If a supplied identity or presentation conflicts with a confirmed market constraint, disclose the exact conflict and let the user choose to use it as-is, provide another source, or authorize an identity-preserving derived presentation reference; keep the gate blocked until that choice is resolved.

For multi-market campaigns, the accepted anchor attestation must name the markets for which it was assessed. Reuse one canonical character identity across compatible markets. If only wardrobe, grooming, styling, or another temporary presentation changes while identity remains the same, create a separately confirmed market-specific derived reference at a new immutable path; do not overwrite the canonical anchor or call the derived version a new baseline. Use distinct canonical characters only when the confirmed creative directions intentionally require distinct identities.

### On-Screen Character Anchor Contract

Every distinct identifiable character planned to appear on screen must have an accepted visual identity anchor **before any storyboard frame or final video containing that character is generated**. Inventory the characters required by the confirmed current-round directions, complete their Market Fit Contract assessment, and resolve each one before the per-video generation package is finalized, in this order:

1. reuse a usable user-provided image of that character as the direct anchor, with zero additional image-generation cost;
2. otherwise reuse the already accepted canonical anchor for that exact character;
3. otherwise, after satisfying the Mandatory Image Knowledge Gate and confirming the paid call, generate a new canonical character anchor under `assets/anchors/canonical/` before generating storyboard frames.

Do not treat a text-only character description, a prior prompt, an unrelated person image, or a scene-composed storyboard frame as an identity anchor. Anonymous non-identifiable background crowds are not characters for this gate, but a hand model, presenter, customer, creator, spokesperson, named role, or any person expected to remain recognizable across shots or batch variants is. When several distinct characters appear, resolve every one separately; do not silently let one anchor stand for another identity.

A generated character anchor must establish the character's original/default identity rather than a story moment: one character only, clearly visible identity features, neutral readable pose and expression, market-appropriate confirmed casting direction plus base wardrobe and styling, no shot-specific action, no product interaction, no story-scene composition, and no text. Its final image prompt must explicitly include the confirmed market-fit scope and the concrete role/audience-relevant visual choices; a market name recorded only in PM state is not model-visible. Present the generated anchor through `present_sandbox_file`, summarize both the identity and intended market scope in conversation, and confirm acceptance through `dynamic_questionnaire` before using it downstream. Close the PM image requirement with the accepted paths, presentation_tool and user_evidence covering market fit and user acceptance. If rejected, revise the anchor first; do not spend storyboard-frame calls on an unconfirmed identity.

Attach the accepted character anchor as actual media to every applicable anchor-dependent image or video call, including each independent one-shot call and every PM-selected Route A contact-sheet batch containing that character. Identify it in image prompts through its ordered `Image[N] (character identity and features to preserve)` mapping. Reassess its recorded market scope when the target market, audience, platform, role, or relevant cultural/category constraint changes; preserve a compatible anchor, create only a needed derived presentation reference, or generate a new intentionally distinct identity after confirmation. The current-round per-video package and final video generation are blocked while any required on-screen character lacks an accepted anchor or current market-fit assessment, even when the user skips the visual storyboard.

### Recurring Scene / Space Anchor Contract

For every current-round video in `visual` mode, inventory the scenes and spaces used by its confirmed shots before generating any related raw storyboard frame. A scene/space anchor is required when the same recognizable environment appears across multiple independent image calls, multiple shots, or multiple contact-sheet batches, or when preserving spatial relationships, layout, set dressing, or brand-identifying environment details is important to continuity. Resolve each required scene in this order:

1. reuse a usable user-provided scene image as the direct anchor, with zero additional image-generation cost;
2. otherwise reuse the already accepted canonical anchor for that exact scene;
3. otherwise satisfy the Mandatory Image Knowledge Gate, disclose why existing media is insufficient and the exact paid image-call count, confirm the paid call through `dynamic_questionnaire`, generate a new canonical scene anchor under `assets/anchors/canonical/`, present it through `present_sandbox_file`, and confirm acceptance through `dynamic_questionnaire` before any related raw-frame call.

Do not generate a normalized or cleaner copy of a usable user-provided scene. A canonical scene anchor is an empty environmental baseline: no characters, no product interaction, no shot-specific story action, and no transient occupancy. It establishes stable architecture, spatial layout, brand-identifying environment details, and default set dressing. Time of day, temporary decoration, occupancy, weather, damage, rearrangement, or another changing condition belongs in a separately cost-confirmed derived-state/continuity reference under `assets/anchors/derived-states/` when that state must persist; it never overwrites or replaces the canonical baseline. Every generated, revised, or replacement media asset uses a new immutable path; close its PM image requirement with a paths list and the required acceptance evidence so PM owns the resulting state change.

A generic one-off background that appears in only one independent image call and has no cross-call spatial, brand, or continuity requirement does not need to be declared as a scene requirement in VideoSpec; record the concrete reason in the blueprint and declaration description. Once a scene requirement is declared, silence, a text-only scene description, a path mentioned in a prompt, a prior raw storyboard frame, or an image attached only to another independent call does not resolve it. Character, product, and scene gates remain separate: do not treat a character anchor or product image as proof of the environment, and do not force paid scene generation for every disposable background.

For every related one-shot or contact-sheet image call, attach each accepted applicable scene anchor as actual media in the final ordered `ImageList` and map it in the prompt through its exact one-based `Image[N] (scene identity, spatial relationships, and features to preserve)` semantics. Before the call, verify the accepted path exists, is non-empty, is not superseded, and matches the scene described by the blueprint for the carried shots. A missing attachment or text/path-only mention blocks the raw-frame call.

### Product View And State Coverage Contract

Before finalizing any current-round per-video generation package or generating any storyboard frame or final video, audit every selected product/SKU against the exact views, physical configurations, opened/closed conditions, removable parts, contents, functional states, and fine details that the confirmed story and current-round directions will visibly require. A front image does not establish an unseen back, side, opening, interior, connector, cap-off state, fill level, folded state, assembled state, or in-use transformation. Treat every SKU separately and never borrow an unshown state or hidden detail from another variant. This gate remains required when the user skips the visual storyboard.

PM makes this audit explicit as `product_state_coverage/<project>/<video>`. First fulfill declared product images through their non-empty paths lists. Fulfill other images using their own allowed resolution; do not treat every image as a product. When the coverage node becomes ready, read those product facts, the complete blueprint and definition, finish any required branch below, and record one final result per declared product through `confirm-product-state-coverage`. Use `covered` for sufficient accepted images, `reference_confirmed` only after presenting and obtaining acceptance for a supplementary generated state reference, or `risk_accepted` only with the explicit evidence and upstream correction described below. Do not record the router answer itself as coverage.

When actual user-provided media covers every required state, reuse all applicable images directly and generate no extra product baseline. When coverage is insufficient, pause before the visual-storyboard choice and all per-video package preparation, then use `dynamic_questionnaire` as a closed routing form with no generic text question:

1. `Upload more product shots (recommended)` - wait for the user to upload the missing views or states, then re-audit them at zero image-generation cost;
2. `Add details and generate a state reference image` - ask for the missing structure, material, color, opening/closing method, removable parts, contents, dimensions, and state differences, summarize those details for confirmation, disclose the required paid image-call count, then generate a reference asset;
3. `Skip and accept the consistency risk` - explain which exact views or states remain unsupported and obtain explicit acceptance before proceeding.

Do not add a custom/other option; the form already supplies one. **The routing answer selects a branch only; it never supplies the branch's required input and never authorizes generation or workflow advancement by itself.** Because the current questionnaire schema has no conditional field visibility, use a mandatory focused follow-up questionnaire for the selected branch unless the routing submission itself already contains the complete required payload, such as actual attached media. A generic `I have confirmed the above information`, `confirm generation`, or repeated branch choice is not a substitute for an actual text response, uploaded image, or explicit risk acceptance.

- Upload branch: request the actual files with a `type: media` question; ask a required SKU/view/state text field only for ambiguity not resolved by the media and accepted facts. The payload form contains no switch/skip radio. Follow the form-level escape and conversation rerouting contract in `dynamic-questionnaire-guide.md`. If the runtime media field cannot upload new files, explicitly ask the user to attach them in conversation and remain stopped. Do not leave `awaiting upload` until at least one actual image is returned or the user explicitly changes branch. Re-audit every received image; if required states remain uncovered, present the remaining gaps and repeat the routing/follow-up flow.
- Detail branch: the next interaction must contain actual `type: text` questions for the missing structure, material, color, dimensions/proportions, opening/closing method, removable parts, contents/fill level, labels, and state differences relevant to that SKU. Empty, generic, or incomplete text leaves the detail dependency open; ask only the unresolved fields again. Once sufficient, summarize the proposed reconstruction, state every assumption and the exact paid call count, then use a separate confirmation form. Only its explicit `Confirm details and generate` response authorizes image generation.
- Skip branch: the next interaction must name the exact unsupported views/states and use a separate risk-confirmation form. Only an explicit `Accept the above consistency risk and continue` response resolves the gate. The initial routing choice alone is not sufficient acceptance.

In all branches, the agent's next PM-directed action after the routing response must be the matching collection or risk-confirmation dependency. Do not load unrelated files, prepare storyboard resources, create anchors, ask a later-stage generation confirmation, or call an image/video tool while the selected branch input is outstanding. If the user chooses generation, do not invent hidden product facts: resolve material unknowns through as many questionnaire turns as needed, then confirm the factual reconstruction and paid calls before using `sandbox_generate_image`. Satisfy the Mandatory Image Knowledge Gate before that call.

Create one accepted **product state reference image** per affected SKU under `assets/anchors/product-states/`. It should cover only the missing views and states needed by the confirmed current round, in a clear neutral product-reference presentation without story scenes, people, decorative claims, or model-rendered labels. When the active image capability can reliably render all required states together, one multi-view call may produce it. Otherwise generate the minimum necessary individual no-text state images and compose them deterministically into one reference image; disclose and confirm the actual image-call count first. Present the completed reference image through `present_sandbox_file`, explain the panel/state order in conversation, and confirm it through `dynamic_questionnaire`. Revise it before the visual-storyboard decision or downstream package preparation when rejected.

If usable user product media exists, it remains authoritative and the generated product state reference is supplementary; attach both to every applicable later image call. If no usable product image exists, the accepted state reference establishes the generated product identity and its confirmed states, but must not contain unconfirmed brand, packaging, label, or structural facts. Refer to every attached source through its actual ordered `Image[N] (SKU, view/state, purpose, and details to preserve)` mapping. Reuse an already accepted state reference without regenerating it while the SKU and required state remain unchanged. A new required state discovered in a later round reopens this gate only for that uncovered state.

The skip-risk choice does not satisfy a declared product requirement. If the user accepts the risk, revise the Direction/video_blueprint and definition so unsupported views or states are no longer required; otherwise obtain real or confirmed generated evidence. Do not claim guaranteed product consistency and do not treat silence or an unrelated confirmation as permission to fabricate product structure.
